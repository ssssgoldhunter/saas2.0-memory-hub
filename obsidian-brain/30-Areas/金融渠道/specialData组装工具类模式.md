# specialData 组装工具类模式（多银行渠道适配）

> 解决什么问题：多银行/多渠道系统里，银行协议细节（键名、必填集、加密口径）泄漏到所有业务
> 调用方——每接一家新银行，所有调用方都要改代码。本模式把"银行知识"收敛到一个组装工具，
> 调用方只填银行无关的标准结构。
> 状态：current（2026-08-17 源于 saas2.0 front 落地，项目侧唯一事实来源：
> saas2.0-memory-hub/docs/saas2.0 重构/15-交易额外数据标准化-spec.md）

## 模式六件套

1. **两段式请求**：`baseData`（银行无关强类型业务字段）+ `specialData`（协议键动态字段）。
   wire 契约只认协议键，组装工具只是协议键的产生方式，不是新契约层。
2. **标准账户结构超集**：pay/rec/oriPay/oriRec + 卡要素/授权要素等嵌套小对象；业务方"有值就填"，
   各银行组装逻辑自己挑字段——取值本身就是分银行的（如会员号 vs 账号），超集让调用方无需感知。
3. **组装工具类 = 实例化工厂**：大对象（数据 + `newPay()/newRec()…` 小对象工厂方法）+ 银行路由工厂
   （platformCode → BankCode → 独立银行组装类，类内按 capability 分发，(bank × capability) 两级寻址）。
   全实例方法零 static；每次组装 new、用完即弃，线程安全靠请求内生命周期。
4. **调用方 check 按能力维度**：不按（银行 × 能力）拆分——标准结构是超集，路由在工具内，
   check 无需银行分支；不同流程引擎/slot 类型才需要拆类。
5. **双层口径**：服务端（交易 API）保留协议键必填校验，作为绕过组装工具直传时的最后防线。
6. **扩展公式**：新增银行 = 枚举 + 一个组装类 + 工厂一个 case；调用方与既有银行零改动。

## 经验教训（通用）

- 协议键名只走常量类（`*ContractKeys`），组装器与消费端双侧禁止字面量——防漂移的唯一手段。
- **纯静态映射不必服务化**：不查库不调银行的组装做成 api 包里的本地工具类即可，
  少一跳网络、少一层故障面；确需服务边界时再服务化（先简单后演进）。
- check 骨架先行、数据收集 TODO 占位：骨架（调用/校验/回填/失败终止）一次写实，
  数据源定型后只补"从哪取值"；**不要提前挂链**——TODO 抛异常的组件挂进在线链路会断生产。
- 协议可选字段（如证件号）做**结构预留不接线**：字段进标准结构、组装器不输出，
  激活 = 组装器加"有则输出"+矩阵补行；结构先行让调用方数据管道提前就绪。
- static 方法本身无并发问题，真正的雷区是共享可变状态；但 static 工具类易被 drift 成有状态，
  实例 + 请求内生命周期是最省心的纪律。
- 同一语义不同协议键名（inAcctNo/acctNo/intAcctNo）**严禁"统一"**——矩阵按 (bank × capability)
  逐格定义，宁可琐碎不可归并。
