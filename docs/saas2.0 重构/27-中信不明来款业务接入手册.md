# 中信不明来款业务接入手册

> 状态：current / verified-against-source
> 核验日期：2026-08-31
> 适用对象：调用 `catering-front` 中信不明来款能力的业务上游开发人员
> 银行范围：仅中信 `platformCode=zxegj`
> 对外契约：全字段强类型请求和返回，不使用 `specialData`

---

## 1. 接入结论

- Feign API：`com.chinaums.front.api.CiticUnidentifiedRemittanceApi`。
- 服务名：`catering-front`。
- 路径前缀：`/front/v1/citic/unidentified-remittances`。
- 提供列表分页查询、统一处理、处理状态查询 3 个入口；统一处理覆盖退款、重新匹配、实时清分。
- 本能力仅属于中信，不进入通用 `FrontCapability`、三域 Registry、LiteFlow 和 `FrontRequest` 两段式模型。
- 请求 DTO 直接继承 `BaseRequest`，由 `FrontSpecialTenantPack` 统一完成租户上下文校验、
  `tenant_base_config` 权威回填和中信账户配置加载。
- 请求和返回均没有 `specialData`；业务字段直接使用 DTO 原始字段。
- 当前 Front 不保存不明来款业务记录，也不更新上游处理状态；调用方负责保存列表记录、处理结果和后续状态。

内部调用链固定为：

```text
CiticUnidentifiedRemittanceApplicationService
→ FrontSpecialTenantPack
→ FrontSpecialProcessContext
→ CiticUnidentifiedRemittanceChannel
→ BankWalletGateway.post
→ 中信 BankWalletSender
```

该专项通过非 LiteFlow 的 `FrontSpecialTenantPack` 复用租户准备，再使用统一 Gateway/Sender；不建立通用
Capability，也不恢复 `TenantBankConfigProvider`。相同 Pack 当前也供中信文件处理专项路径使用。

### 1.1 最终协议基线

本功能以记忆库中的专项 Word 文档为最终协议标准：

```text
docs/中信E管家产品V2_不明来账_客户钱包应用平台_接口文档-内部集成平台.doc
```

lsym UAT 的 `ZxTransQueryService/ZxTransQueryServiceImpl/ZxTransServiceImpl` 用于核对真实调用形态。
最终采用的中信交易码为：

| 业务 | API 后缀 | `bizFunc` | `chnlNo` |
|---|---|---:|---:|
| 不明来款列表 | `query-trans-details` | `2033` | `0010` |
| 不明来款退款 | `refund` | `2025` | `0010` |
| 重新匹配/实时清分 | `recharge` | `2023` | `0010` |
| 不明来款状态 | `query-trans-status` | `2087` | `0010` |

综合中信文档中的 `recharge+bizFunc=24` 和 `query-trans-status+bizFunc=123` 是另一套协议，
本功能不采用。专项文档封面显示 V2.3、版本历史为 0.1；“V5.5”是平安项目总文档版本，不能作为
本功能的中信协议版本。

## 2. 公共接入准备

### 2.1 Maven 与 Feign

```xml
<dependency>
    <groupId>com.chinaums</groupId>
    <artifactId>catering-api-front</artifactId>
    <version>${project.version}</version>
</dependency>
```

```java
private final CiticUnidentifiedRemittanceApi unidentifiedRemittanceApi;
```

业务上游不得复制 API、DTO 或枚举，也不得自行调用中信钱包地址。

### 2.2 租户公共字段

所有请求均直接包含以下四个公共字段：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `tenantId` | String | 是 | Header 和请求体都必须存在且一致；Header 是强制权威值，请求体不能替代 Header |
| `clientId` | String | 否 | 缺失时从 `tenant_base_config` 回填 |
| `platformCode` | String | 否 | 缺失时回填；最终必须为 `zxegj` |
| `dataSourceId` | String | 否 | 配置非空时：缺失则回填、不一致则失败；配置为空时保持请求值；专项能力当前不访问业务分库 |

请求体值与 Header 或租户配置值冲突时明确失败，不静默覆盖。以下银行静态字段只由 Front 内部获取，
调用方不得传入：

```text
appId / appKey / url / mchntId / mchntMbrId / bizFunc / chnlNo / accountConfig / settleInfo
```

### 2.3 返回判断

列表接口直接返回 `TableDataInfo<CiticUnidentifiedRemittanceItem>`；处理和状态接口返回 `R<T>`。

```java
R<CiticUnidentifiedProcessResult> response = unidentifiedRemittanceApi.process(request);
if (response == null || response.getCode() != R.SUCCESS || response.getData() == null) {
    throw new IllegalStateException(response == null ? "Front无响应" : response.getMsg());
}
if (!"200".equals(response.getData().getFrontRespCode())) {
    throw new IllegalStateException(response.getData().getFrontRespDesc());
}
```

不能只看 HTTP 200。银行业务失败时顶层 `R.code=500`，但 `data` 可能仍存在，用于取得银行原始失败说明；
参数或租户配置失败发生在银行调用前，`data` 为空。

## 3. 不明来款列表分页查询

```text
POST /front/v1/citic/unidentified-remittances/pages
CiticUnidentifiedQueryRequest → TableDataInfo<CiticUnidentifiedRemittanceItem>
银行：query-trans-details + bizFunc=2033 + chnlNo=0010
```

### 3.1 请求字段

除 §2.2 的四个公共字段外：

| 字段 | 类型 | 必填 | 格式/取值 | 说明 |
|---|---|---|---|---|
| `beginDate` | String | 是 | `yyyyMMdd` | 查询开始日期 |
| `transDate` | String | 是 | `yyyyMMdd` | 查询结束日期，映射银行补充域 `transDate` |
| `transStatus` | String | 否 | `0/1/9` | 0 未处理、1 处理成功、9 全部；缺省 9 |
| `pageNo` | Integer | 否 | `>=1` | 起始页，缺省 1 |

`beginDate` 不得晚于 `transDate`。Front 从 `pageNo` 开始循环调用银行直到 `totalPage`，把这些页的
明细聚合到一次响应中；因此 `rows` 不是固定 20 条。若从第 2 页开始，`rows` 只包含第 2 页至末页，
但 `total` 仍是银行返回的全部记录数。

### 3.2 请求示例

```json
{
  "tenantId": "80001",
  "beginDate": "20260801",
  "transDate": "20260824",
  "transStatus": "0",
  "pageNo": 1
}
```

### 3.3 返回外壳

| 字段 | 类型 | 说明 |
|---|---|---|
| `total` | long | 银行 `totalNum`，全部记录数 |
| `totalPage` | Long | 银行总页数 |
| `rows` | List | 从起始页到最后一页的聚合明细，失败时为空数组 |
| `code` | int | 200 成功，500 失败 |
| `msg` | String | 查询说明或安全失败信息 |
| `extraData` | Map | 当前未使用 |

每条 `CiticUnidentifiedRemittanceItem` 的完整字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `remittanceId` | String | 来款编号 |
| `bankSerialNo` | String | 银行侧唯一流水号 |
| `payAccyNo` | String | 来账账号，银行 SM2 密文原样返回 |
| `payAccyNm` | String | 来账户名，银行 SM2 密文原样返回 |
| `acctNo` | String | 交易资金账号，银行返回原值 |
| `timeStampe` | String | 时间戳，后续处理和状态查询复用 |
| `remittanceNote` | String | 来款附言 |
| `accountType` | String | 0 客户账、1 内部账 |
| `transDate` | String | 来账交易日期 `yyyyMMdd` |
| `transJrno` | String | 交易日志号，退款、匹配和状态查询的原交易定位值 |
| `oppositeBankNo` | String | 对方行号，退款使用 |
| `transAmt` | Long | 交易金额，人民币分 |
| `acctSeq` | String | 账户序号，客户账主键字段 |
| `bankNo` | String | 银行号，客户账主键字段 |
| `acctTransNo` | String | 账户交易序号，客户账主键字段 |
| `finTransFlag` | String | 金融交易标识，客户账主键字段 |
| `remark` | String | 银行备注 |
| `transStatus` | String | 0 未处理、1 处理成功、2 处理中 |

专项文档使用 `payAccyNo/payAccyNm`，lsym UAT DTO 使用 `payAcctNo/payAcctNm`。Front 解析时优先读取
专项文档键，缺失时兼容 UAT 拼写，对外统一返回 `payAccyNo/payAccyNm`。

## 4. 不明来款统一处理

```text
POST /front/v1/citic/unidentified-remittances/process
CiticUnidentifiedProcessRequest → R<CiticUnidentifiedProcessResult>
```

### 4.1 公共和条件字段

| 字段 | 类型 | 退款 0 | 重新匹配 1 | 实时清分 2 | 说明 |
|---|---|---:|---:|---:|---|
| `operateType` | enum | 必填 | 必填 | 必填 | `0/1/2` |
| `accountType` | enum | 必填 | 必填 | 必填 | `0` 客户账、`1` 内部账 |
| `acctNo` | String | 必填 | 必填 | 必填 | 明文传 Front，Front SM2 加密上送 |
| `timeStampe` | String | 必填 | 必填 | 必填 | 取列表同名字段 |
| `oriTransSsn` | String | 必填 | 不使用 | 不使用 | 取列表 `transJrno` |
| `oriTransDate` | String | 必填 | 不使用 | 不使用 | 取列表 `transDate`，`yyyyMMdd` |
| `transAmt` | Long | 必填且大于 0 | 选填 | 选填 | 人民币分 |
| `oppositeBankNo` | String | 必填 | 选填 | 选填 | 取列表同名字段 |
| `transDate` | String | 不使用 | 必填 | 必填 | 取列表同名字段，`yyyyMMdd` |
| `transJrno` | String | 不使用 | 必填 | 必填 | 取列表同名字段 |
| `registerType` | enum | 不使用 | 选填 | 必填 | `01` 用户登记簿、`02` 担保登记簿 |
| `userId` | String | 不使用 | 选填 | 必填 | 01 传用户编号，02 传商户编号；Front SM2 加密 |

当 `accountType=0`（客户账）时，以下四个字段对三种操作都必填；`accountType=1` 时可空：

| 字段 | 来源 |
|---|---|
| `bankNo` | 列表 `bankNo` |
| `acctSeq` | 列表 `acctSeq` |
| `acctTransNo` | 列表 `acctTransNo` |
| `finTransFlag` | 列表 `finTransFlag` |

### 4.2 退款示例

```json
{
  "tenantId": "80001",
  "operateType": "0",
  "accountType": "0",
  "acctNo": "J04069400000302",
  "oriTransSsn": "20260824001234",
  "oriTransDate": "20260824",
  "transAmt": 10000,
  "oppositeBankNo": "102100099996",
  "timeStampe": "2026-08-24-14.30.57.000001",
  "bankNo": "102",
  "acctSeq": "000001",
  "acctTransNo": "0000000000001",
  "finTransFlag": "1"
}
```

Front 调用 `/refund + bizFunc=2025`，固定上送 `operateType=0`。

### 4.3 重新匹配示例

```json
{
  "tenantId": "80001",
  "operateType": "1",
  "accountType": "0",
  "acctNo": "J04069400000302",
  "transDate": "20260824",
  "transJrno": "20260824001234",
  "transAmt": 10000,
  "timeStampe": "2026-08-24-14.30.57.000001",
  "bankNo": "102",
  "acctSeq": "000001",
  "acctTransNo": "0000000000001",
  "finTransFlag": "1"
}
```

重新匹配不要求 `userId/registerType`。Front 调用 `/recharge + bizFunc=2023`，专项字段进入银行

### 4.4 实时清分示例

```json
{
  "tenantId": "80001",
  "operateType": "2",
  "accountType": "1",
  "acctNo": "J04069400000302",
  "transDate": "20260824",
  "transJrno": "20260824001234",
  "timeStampe": "2026-08-24-14.30.57.000001",
  "registerType": "01",
  "userId": "USER0001"
}
```

Front 调用 `/recharge + bizFunc=2023`，固定 `operateType=2`。`userId` 在 Front 内完成 SM2 加密。
示例为内部账，因此不要求客户账四字段。

## 5. 不明来款处理状态查询

```text
POST /front/v1/citic/unidentified-remittances/status
CiticUnidentifiedStatusRequest → R<CiticUnidentifiedStatusResult>
银行：query-trans-status + bizFunc=2087 + chnlNo=0010
```

### 5.1 请求字段

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `oriTransSsn` | String | 是 | 必须取列表 `transJrno`，不是处理结果 `frontSsn` |
| `oriTransDate` | String | 是 | 必须取列表 `transDate`，`yyyyMMdd` |
| `acctNo` | String | 是 | 取列表交易资金账号；Front SM2 加密 |
| `accountType` | enum | 是 | 0 客户账、1 内部账 |
| `transAmt` | Long | 是 | 原来款金额，人民币分且大于 0 |
| `timeStampe` | String | 是 | 取列表同名字段 |
| `acctSeq` | String | 客户账必填 | 取列表同名字段 |
| `bankNo` | String | 客户账必填 | 取列表同名字段 |
| `acctTransNo` | String | 客户账必填 | 取列表同名字段 |
| `finTransFlag` | String | 客户账必填 | 取列表同名字段 |

### 5.2 请求示例

```json
{
  "tenantId": "80001",
  "oriTransSsn": "20260824001234",
  "oriTransDate": "20260824",
  "acctNo": "J04069400000302",
  "accountType": "0",
  "transAmt": 10000,
  "timeStampe": "2026-08-24-14.30.57.000001",
  "acctSeq": "000001",
  "bankNo": "102",
  "acctTransNo": "0000000000001",
  "finTransFlag": "1"
}
```

### 5.3 返回字段和状态

`CiticUnidentifiedStatusResult` 继承处理结果公共字段，并增加：

| 字段 | 类型 | 说明 |
|---|---|---|
| `status` | enum | `0` 未处理、`1` 成功、`2` 处理中 |
| `bankStatus` | String | 银行原始 `oriTransStatus`，与 `status` code 一致 |

`R.code=200/frontRespCode="200"` 只说明状态查询成功；最终业务结果必须再读取 `status`。状态为 `0`
不能当作接口失败，状态为 `2` 不能重发处理请求。

```json
{
  "code": 200,
  "msg": "操作成功",
  "data": {
    "frontRespCode": "200",
    "frontRespDesc": "成功",
    "queryId": "Q202608240002",
    "bankStatus": "2",
    "bankSerialNo": "ZX202608240001",
    "status": "2"
  }
}
```

银行成功响应缺少 `oriTransStatus` 或返回其他未知值时，Front 按钱包响应格式错误处理，不伪装成功。

## 6. 推荐业务接入流程

```text
1. queryPages 查询 transStatus=0 的未处理来款
2. 业务上游保存列表原行及处理状态
3. 用户选择退款 / 重新匹配 / 实时清分
4. 从原行复制定位字段组装 process 请求
5. 处理成功后保存 queryId/bankSerialNo/frontSsn，但不要替换原 transJrno/transDate
6. 需要确认银行状态时，用原行 transJrno/transDate 调 queryStatus
7. 按 status=0/1/2 更新上游业务状态
```

重要边界：

- Front 不判断某笔来款是否允许退款或匹配，不负责上游审批、操作员、门店和机构权限；
- Front 不保存不明来款业务表或操作日志；上游必须自行保证同一来款不会被并发重复处理；
- Front 不自动重试处理请求；调用超时或状态不明确时先查询状态；
- 列表的 `processingStatus/processingMethod/processingStaff/orgCode` 等旧 lsym 本地字段不是银行返回，
  不在 Front DTO 中；这些字段由新业务上游自行维护。

## 7. 错误处理

### 7.1 列表失败

```json
{
  "total": 0,
  "totalPage": 0,
  "rows": [],
  "code": 500,
  "msg": "中信不明来款列表应答缺少 totalPage",
  "extraData": null
}
```

### 7.2 处理或状态查询失败

银行明确拒绝时保留专属结果：

```json
{
  "code": 500,
  "msg": "原交易不存在",
  "data": {
    "frontRespCode": "F400004",
    "frontRespDesc": "原交易不存在",
    "queryId": "Q202608240003",
    "bankStatus": "0",
    "frontSsn": "J0406942026082414305700000002",
    "operateType": "0"
  }
}
```

请求字段、租户配置或中信账户配置错误发生在银行调用前，返回 `R.fail(message)` 且 `data=null`。
上游应记录业务定位号和安全错误说明，不记录完整请求、响应、账号、户名或密钥。Front 内部最终 Sender
仍按统一口径记录完整明文钱包请求/响应 body，其他 Front 层和上游不得重复。

## 8. 安全与联调检查

- `acctNo/userId` 对 Front 为明文业务字段，Front 在银行请求映射器中完成 SM2 加密；调用方不要预加密。
- 列表 `payAccyNo/payAccyNm/acctNo` 按银行原值返回，可能是银行 SM2 密文；Front 不解密、不脱敏。
- 上游及 Front 非 Sender 业务日志禁止输出完整请求、响应、账户、户名、密钥或银行账户配置；最终
  Sender 唯一记录完整明文钱包 body，`appKey`、私钥、签名材料和认证 Header 等非业务报文凭证不记录。
- `transAmt` 对外统一为 `Long` 人民币分，禁止使用 `double/float`。
- 联调时先验证内部账，再验证客户账四字段是否完整进入 `2023 reserve` 和 `2087` 请求。
- 确认银行返回键最终使用 `payAccyNo/payAccyNm` 还是 UAT 的 `payAcctNo/payAcctNm`；当前 Front 两套兼容，
  联调确认后再决定是否删除回退，不在业务上游写双键逻辑。
