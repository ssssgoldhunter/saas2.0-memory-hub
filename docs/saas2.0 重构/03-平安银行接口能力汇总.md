## 2. 接入协议摘要

### 2.1 地址与报文

接口地址组成：

```text
域名前缀 + 业务后缀
```

文档示例：

```text
测试环境：https://test-api-open.chinaums.com/v1
生产环境：https://api-mop.chinaums.com/v1
```

平安相关业务路径统一位于：

```text
/cwap/account/send/{业务后缀}
```

公共约束：

- 平安见证宝渠道号固定为 `0001`；
- 请求和响应使用 JSON；
- `reserve` 是 JSON 格式补充域；
- 金额通常以分为单位；
- 日期一般为 `yyyyMMdd`；
- 时间一般为 `HHmmss` 或完整 `yyyyMMddHHmmss`。

### 2.2 认证与敏感信息

- 每笔请求在 HTTP 头携带 `Authorization`；
- 姓名、卡号、手机号、证件号、短信验证码等敏感字段使用 SM2；
- SM2 曲线为 `sm2p256v1`；
- 资金汇总账户、见证子账户、银行卡号、户名等字段按接口要求加密；
- Front 必须集中完成加密，业务系统不能传已拼装的完整银行请求。

### 2.3 平安交易流水

大多数联机接口的 `transSsn`：

```text
接入方编号（6位）+ MMDD（4位）+ 12位序列
总长度 22 位
```

要求永久唯一。Front 应独立生成银行请求流水，并与 `frontSsn` 建立映射。

## 3. 公共请求与响应字段

### 3.1 公共请求字段

| 字段 | 含义 | Front 归属 |
|---|---|---|
| `transSsn` | 银行请求流水号 | Front 生成 |
| `transTime` | 请求发送时间 | Front 生成 |
| `mchntId` | 接入方编号 | 租户银行配置 |
| `mchntMbrId` | 商户会员编号 | 配置或业务核心数据，按接口确定 |
| `bizFunc` | 平安业务用途 | 平安 Handle 确定 |
| `chnlNo` | 平安渠道号，固定 `0001` | 平安 Handle 确定 |
| `acctNo` | 账户号或见证子账户 | 业务核心数据，经加密 |
| `outAcctNo` | 转出账户 | 业务核心数据，经加密 |
| `inAcctNo` | 转入账户 | 业务核心数据，经加密 |
| `transAmt` | 交易金额，单位为分且包含手续费 | `baseData.amount` |
| `fee` | 手续费，单位为分 | `baseData.fee` |
| `ccy` | 币种 | Handle 默认或核心数据 |
| `remark` | 备注 | 业务核心数据 |
| `reserve` | 平安业务补充域 | Handle 显式映射 |

### 3.2 公共响应字段

| 字段 | 含义 | Front 建议映射 |
|---|---|---|
| `errCode` | 钱包平台返回码 | 只用于平台层成功判定并保存渠道流水，不直接透传 |
| `errInfo` | 钱包平台返回说明 | 只用于平台层成功判定并保存渠道流水，不直接透传 |
| `queryId` | 见证系统或前置查询流水 | `frontQueryId` |
| `sysRespCode` | 平安渠道返回码 | 银行结果码 |
| `sysRespDesc` | 平安渠道返回说明 | 银行结果说明 |
| `status` | 公共状态，多个用途标注忽略 | 不直接作为终态 |
| `reserve` | 平安扩展响应 | 具体响应解析器使用 |

现有接入的平安成功条件是 `errCode=D5000000 && errInfo=success && sysRespCode=000000`。
其中平安 `sysRespCode` 成功码是 **6 个 0**，不同于中信的 5 个 0。上述原始值必须转换为
`FrontErrorCode`，真实成功统一返回 `200/成功`。

平安部分交易同步只返回“受理成功”，特别是提现。Front 必须区分：

```text
受理成功 != 银行最终成功
```

## 5. 当前交易业务详细摘要

### 5.1 消费与普通转账

银行接口：

```text
POST /cwap/account/send/transfer
bizFunc = 01
chnlNo = 0001
银行产品 = 会员间交易-不验证（6034）
```

`functionFlag`：

| 值 | 含义 |
|---:|---|
| 6 | 直接支付 T+1 |
| 7 | 免密支付 |
| 9 | 直接支付 T+0 |

公共字段：

- 转出、转入见证子账户；
- 转出、转入会员编号及户名；
- 交易金额 `baseData.amount`，单位为分，映射 `transAmt` 且包含手续费；
- 手续费 `baseData.fee`，单位为分，映射 `fee`，无手续费传 0；
- 币种；
- 订单号；
- 交易类型；
- 备注。

平安 `reserve` 主要字段：

| 字段 | 说明 |
|---|---|
| `mrchCode` | 平台号 |
| `txnClientNo` | 客户号 |
| `functionFlag` | T+1、免密或 T+0 模式 |
| `stlAcctNo` | 资金汇总账号，来自平安 `accountSpecialData`，Handle 使用前进行 SM2 加密 |
| `outAcctId` | 转出方会员编号 |
| `outAcctName` | 转出方户名，SM2 加密 |
| `inAcctId` | 转入方会员编号 |
| `inAcctName` | 转入方户名，SM2 加密 |
| `transType` | 交易类型 |
| `orderId` | 业务订单号 |
| `orderInfo` | 订单内容，consume 优先取 `baseData.orderInfo` |

适配结论：

- 消费和普通转账可复用同一个底层银行接口；
- Front 业务类型、订单类型和渠道流水仍应区分；
- `functionFlag` 会改变结算和退款语义，必须由平安 Handle 根据已确认的 Front 业务场景选择，
  不能由业务系统任意透传银行原值；
- 不建议继续使用含义不清的 `bankChannelNo=0107/0109` 对业务模式编码。

平安 transfer/consume 当前没有确认必须返给业务系统的银行特有字段，因此成功响应的
`specialData` 默认为空；后续只能将契约白名单内的响应字段逐项写入，禁止整体透传 `reserve`。

### 5.2 短信鉴权转账

交易接口：

```text
POST /cwap/account/send/transfer
bizFunc = 45
银行产品 = 会员间交易-验证短信动态码（6101）
```

验证码申请：

```text
POST /cwap/account/send/gen-auth-code
bizFunc = 26
银行产品 = 申请提现或支付短信动态码（6082）
```

验证码申请主要字段：

| 钱包字段 | 当前 Front 来源 | 说明 |
|---|---|---|
| `mchntMbrId` | `baseData.payerMemberId` | 付款方交易网会员代码 |
| `acctNo` | `baseData.payerAccountId` | 转出见证子账户，SM2 加密 |
| `transAmt` | `baseData.amount` | 交易金额，Front 统一按人民币分 |
| `mrchCode/txnClientNo` | 平安账户 `accountSpecialData` | 平台号、客户号，禁止业务请求覆盖 |
| `stlAcctNo` | 平安账户 `accountSpecialData` | 资金汇总账户，SM2 加密 |
| `tranType` | Handle 固定 `2` | 当前 Front 仅使用支付分支 |
| `orderNo` | `baseData.bizOrderNo` | 业务主订单号 |
| `remark` | `baseData.remark` | 业务备注 |
| `intAcctNo` | `baseData.payeeAccountId` | 转入方见证子账户，SM2 加密；`int` 是银行协议原始拼写 |

短信鉴权转账 `reserve` 主要字段：

| 字段 | 说明 |
|---|---|
| `mrchCode`、`txnClientNo` | 平台、客户标识 |
| `stlAcctNo` | 资金汇总账户 |
| `functionFlag` | 文档支持直接支付 T+1/T+0 |
| `outMemberCode` | 转出会员代码 |
| `outSubAcctName` | 转出子账户名称 |
| `inMemberCode` | 转入会员代码 |
| `inSubAcctName` | 转入子账户名称 |
| `tranType` | 交易类型 |
| `orderNo` | 订单号 |
| `messageOrderNo` | 短信指令号 |
| `messageCheckCode` | 短信验证码，SM2 加密 |

重要结论：

- 文档证明的是“短信鉴权转账”，不是“授信额度转账”；
- `transferAuth` 当前固定 `bizFunc=45/chnlNo=0001/functionFlag=9/tranType=01`；
- `resendTransferAuthCode` 固定 `bizFunc=26/chnlNo=0001/tranType=2`；
- 文档定义“申请验证码”，没有独立“重发”银行接口；Front 的重发语义是生成新的银行流水后再次
  调用申请接口，不上送旧 `smsIdx`；
- `bizFunc=26` 返回的 `smsIdx/receiveMobile` 均为 SM2 密文，Handle 解密后按白名单写入返回
  `specialData`，禁止写日志；
- `transferAuth` 请求的 `messageOrderNo/messageCheckCode` 放在请求 `specialData`，验证码由 Handle
  加密，基础对象不增加平安私有字段；
- 重复申请的限流、有效期和旧验证码失效规则仍需联调确认。

### 5.3 提现

统一 API：

```text
POST /cwap/account/send/withdrawal
```

两种用途：

| `bizFunc` | 能力 | 特点 |
|---:|---|---|
| 01 | 会员提现-不验证 `6033` | 直接申请提现 |
| 36 | 会员提现-支持手续费 `6085` | 支持平台手续费和短信验证 |

`bizFunc=01` 关键数据：

- 见证子账户；
- 收款银行卡；
- 提现金额；
- 会员、证件、户名信息；
- 资金汇总账户；
- 平台号、客户号。

`bizFunc=36` 关键数据：

- 见证子账户及户名；
- 收款账户账号、户名；
- 提现金额；
- 市场收取的手续费；
- 短信指令号、短信验证码；
- 资金汇总账户；
- 可选网银签名。

重要状态语义：

- 同步响应表示提现请求被受理；
- 最终成功需调用 `query-trans-status` 的 `bizFunc=03`；
- 提现成功后仍可能发生退票；
- 退票信息需通过 `query-trans-details` 的 `bizFunc=02` 查询。

### 5.4 退款

统一 API：

```text
POST /cwap/account/send/refund
```

| `bizFunc` | 原交易范围 | 说明 |
|---:|---|---|
| 02 | 6006/6034/6101 的直接支付，文档列出 `functionFlag=6/9` | 会员间交易退款 |
| 06 | 6163/6165/6166 会员资金支付 | 会员资金支付退款 |

关键字段：

- 原交易流水号；
- 原交易日期；
- 退款金额；
- 退款手续费；
- 原支付订单号；
- 退款订单号；
- 卖方、买方见证子账户；
- 平台号、客户号；
- 退款垫款户或手续费相关信息。

已发现的关键问题：

- 文档明确列出的直接支付退款范围是 `functionFlag=6/9`；
- 5.5 新增的免密支付为 `functionFlag=7`；
- 文档没有同步明确 `functionFlag=7` 的退款处理方式；
- Front 在支持免密消费退款前必须向银行确认。

退款 Handle 应优先根据原 `frontSsn` 查询渠道流水，并根据原交易使用的银行用途自动选择 `bizFunc=02/06`。

### 5.5 平台付款与平台收款

平安文档中存在：

- `bizFunc=02` 补贴；
- `bizFunc=01` 会员间交易；
- `bizFunc=46` 会员资金支付；
- 子账户登记挂账等能力。

但没有发现与中信以下能力在账户方向和账簿语义上完全等价的成对接口：

```text
2041 平台付款：平台自有资金登记簿 → 用户登记簿
2042 平台收款：用户登记簿 → 平台自有资金登记簿
```

因此：

- 不能直接将平安“补贴”等同于平台付款；
- 不能直接将普通会员间转账等同于平台收款；
- 需要明确平安侧平台自有账户、营销账户、资方账户、挂账账户的资金模型；
- 未确认前建议能力矩阵标记为 `UNSUPPORTED` 或 `PENDING_CONFIRMATION`。

## 6. 当前账户查询详细摘要

### 6.1 账户信息查询

API：

```text
POST /cwap/account/send/query-acct-info
```

| `bizFunc` | 能力 | 主要字段 |
|---:|---|---|
| 01 | 根据会员代码查询会员子账户 | 会员代码、资金汇总账户 |
| 63 | 查询资金汇总账户余额 | `stlAcctNo`、平台号、客户号 |
| 64 | 查询会员子账户 | 会员编号或子账户定位信息 |

主要返回信息可能包括：

- 见证子账户账号；
- 账户类型；
- 可用余额；
- 可提现余额；
- 冻结金额；
- 资金汇总账户当前余额、上日余额；
- 会员及账户基础信息。

### 6.2 账户信息列表查询

API：

```text
POST /cwap/account/send/query-acct-info-list
```

| `bizFunc` | 能力 |
|---:|---|
| 01 | 普通会员子账户余额 |
| 02 | 功能子账户余额 |
| 03 | 会员子账户余额 `6093` |

需要注意：

- 旧代码采用了 `bizFunc=03`；
- 文档同一部分同时出现 `01/02/03`，但部分请求或响应说明只标注 `01/02`；
- 新实现前应确认三种用途的准确边界和正式投产值。

### 6.3 账户状态

平安账户查询响应中存在 `acctState` 等字段，但文档多个位置标注为忽略，未发现与中信 `2058 用户状态查询` 完全等价的独立能力。

因此 Front 的 `queryAccountStatus`：

- 中信可以返回明确用户状态；
- 平安不能仅以“账户查询成功”模拟用户状态正常；
- 如产品要求统一账户状态，需要银行提供正式状态字段和枚举。

## 7. 当前交易查询详细摘要

### 7.1 交易状态查询

API：

```text
POST /cwap/account/send/query-trans-status
```

当前交易相关映射：

| Front 原交易类型 | 平安 `bizFunc` |
|---|---:|
| 普通转账、消费、短信鉴权转账 | 02 |
| 提现 | 03 |
| 充值 | 04 |
| 特定批量、冻结、补贴、分账终态 | 06 |

主要请求字段：

- 原交易流水号 `oriTransSsn`；
- 原交易日期 `oriTransDate`；
- 部分用途要求资金汇总账户；
- 平台号、客户号等补充信息。

银行原交易状态：

| `oriTransStatus` | 含义 | Front 建议 |
|---:|---|---|
| 0 | 成功 | `SUCCESS` |
| 1 | 失败 | `FAILED` |
| 2 | 待确认 | `UNKNOWN` 或 `PROCESSING` |
| 5 | 待处理 | `PROCESSING` |
| 6 | 处理中 | `PROCESSING` |

文档提示：返回值不是 0 或 1 时应视为状态未明，约 5 分钟后再次查询。

适配结论：

- `bizFunc` 应由原渠道流水的交易类型决定；
- 调用方优先传 `originalFrontSsn`，而不是传 `02/03`；
- Front 需要定义查询重试、超时和最终人工处理边界。

### 7.2 平台普通转账充值明细

```text
POST /cwap/account/send/query-trans-details
bizFunc = 04
银行产品 = 查询普通转账充值明细（6050）
```

用途：

- 查询会员主动转账进入资金汇总账户的明细；
- 已绑定账号可自动入账会员子账户；
- 未绑定账号可能进入挂账子账户；
- 可查询见证+收单的 T0 充值记录。

请求扩展：

- `functionFlag=1` 当日、`2` 历史；
- `stlAcctNo`；
- `page`；
- `mrchCode`、`txnClientNo`。

该接口只覆盖平安平台入金的一部分，不能直接等价为中信 `bizFunc=25` 的所有平台交易类型。

### 7.3 子账户时间段交易明细

```text
POST /cwap/account/send/query-trans-details
bizFunc = 05
银行产品 = 查询时间段内会员成功交易（6072）
```

请求：

| 字段 | 说明 |
|---|---|
| `functionFlag` | `1` 当日；`2` 历史 |
| `stlAcctNo` | 资金汇总账户 |
| `subAcctNo` | 见证子账户 |
| `queryFlag` | `1` 全部；`2` 转出；`3` 转入 |
| `pageNum` | 页码，每页最多 20 条 |
| `mrchCode`、`txnClientNo` | 平台和客户标识 |

关键响应：

- 转出/转入方向；
- 交易金额；
- 交易日期、时间；
- 见证系统流水；
- 记账类型；
- 转入、转出子账户；
- 备注；
- 分页信息。

记账类型可能包含支付、冻结、解冻、登记挂账、预支付、确认付款、退款以及见证+收单相关类型。

### 7.4 清分、提现和退款明细

```text
POST /cwap/account/send/query-trans-details
bizFunc = 08
银行产品 = 查询时间段内清分提现明细（6073）
```

`queryFlag`：

| 值 | 含义 |
|---:|---|
| 2 | 提现及相关退款记录 |
| 3 | 清分、充值 |
| 4 | 收款编码退款 |

关键响应：

- 提现/清分标志；
- 交易状态；
- 会员代码；
- 见证子账户；
- 交易金额；
- 手续费；
- 交易日期、时间；
- 见证系统流水；
- 备注。

### 7.5 提现退票

```text
POST /cwap/account/send/query-trans-details
bizFunc = 02
银行产品 = 查询提现退单信息（6048）
```

关键响应：

- 原提现交易流水；
- 原提现见证流水、市场流水；
- 退票原因、退票日期；
- 退票入账流水和金额；
- 付款账号、户名、银行；
- 收款方见证子账户；
- 业务流水号。

该能力应作为提现终态处理的一部分，而不是普通明细列表的可选字段。

### 7.6 平台交易查询与中信的差异

中信平台资金账户明细 `25` 可按以下类型直接筛选：

```text
渠道实收、转账、退汇、提现、所有
```

平安没有一个接口同时提供完全相同的分类：

- 入金在 `04`；
- 会员交易在 `05`；
- 提现、清分、部分退款在 `08`；
- 提现退票在 `02`；
- 银行费用在 `39`。

所以平安 `queryPlatformTransactions` 需要明确选择：

1. 只支持某些通用类型；
2. 根据通用类型调用不同 `bizFunc`；
3. 对“所有”发起多个银行查询并聚合。

在没有确定分页、排序、去重和超时规则前，不建议首期实现跨多个 `bizFunc` 的“所有交易”聚合。

## 8. Front 适配结论

### 8.1 建议的平安 Handle 能力

```text
PingAnTransactionHandle
  - consume
  - transfer
  - transferWithSms
  - applyTransferSmsCode
  - withdraw
  - refund
  - platformPay          // 待确认或不支持
  - platformReceive      // 待确认或不支持

PingAnAccountHandle
  - queryPlatformBalance
  - querySubAccountBalance
  - queryFunctionalAccountBalances
  - queryAccountStatus   // 待确认

PingAnQueryHandle
  - queryTransactionStatus
  - queryPlatformTransactions
  - querySubAccountTransactions
  - queryWithdrawReturn
```

### 8.2 大 Query Handle 的内部结构

`QueryRouter` 只按 `platformCode` 获取 `PingAnQueryHandle`。业务能力由具体方法确定：

```java
queryRouter.get(platformCode)
    .queryTransactionStatus(context, request);

queryRouter.get(platformCode)
    .queryPlatformTransactions(context, request);

queryRouter.get(platformCode)
    .querySubAccountTransactions(context, request);
```

如果对外只提供一个通用 `/query`，则 `QueryCapability` 必须存在于核心业务请求，但仍不进入 Route Key。

### 8.3 `specialData` 边界

可以放入：

- 银行特有的可选订单内容；
- 经契约定义的平安扩展备注；
- 暂时没有进入公共核心对象的条件字段；
- 特定查询接口的可选筛选扩展。

不应放入：

- `bizFunc`、`chnlNo`；
- `mchntId`、`appIdBank`、`appKeyBank`；
- `txnClientNo`、`mrchCode`、`stlAcctNo` 等平安账户静态配置；
- URL、签名算法、加密算法、密钥；
- `functionFlag` 对应的业务模式原始码；
- `queryFlag`、查询场景等已定义为公共语义的字段；
- Front 流水号或银行流水号生成规则。

### 8.4 渠道流水作用

渠道流水除审计外，还需要保存：

- 原交易的平安 `bizFunc`；
- `functionFlag`；
- 提现模式 `01/36`；
- 银行 `transSsn`、`queryId`；
- 原 `frontSsn`；
- 业务主、子订单；
- 同步受理状态和最终状态；
- 退款使用的原交易类型。

这样状态查询、退款和提现退票查询才能由 Front 自动选择正确银行能力。

## 9. 已发现的风险和待确认项

1. 源文件名为 5.5、封面为 5.4，需要确认正式投产版本。
2. `functionFlag=7` 免密支付已经增加，但退款章节只明确 `6/9`，需确认免密退款。
3. “授信转账”应改为“短信鉴权转账”，除非银行另有授信额度类产品。
4. 验证码重发已约束为再次调用申请接口，但限流、旧验证码失效及有效期仍需联调确认。
5. 提现需要确认首期支持 `01`、`36` 还是两者。
6. 提现同步成功只是受理成功，必须查询状态并处理退票。
7. 平台付款、平台收款没有与中信 `2041/2042` 完全等价的接口。
8. 账户列表查询 `01/02/03` 的文档描述存在交叉，需确认正式 `bizFunc`。
9. 交易明细目录列出 `bizFunc=43`，公共请求说明主要列到 `40`，需确认 `43` 是否投产。
10. 平安平台交易查询需要跨 `04/05/08/02/39`，不能简单套用中信类型。
11. 平安缺少已确认的中信 `2058` 等价账户状态查询。
12. 平安不同查询用途的返回数组结构不同，必须按用途使用独立响应解析器。
