## 1A. 接口字段公用化方案（2026-08-21 用户要求：字段参考 transfer/consume 尽量公用、流程先转换后请求）

### 1A.0 公用化流程（两接口与 transfer/consume 完全一致）

```text
① 收集标准结构（pay / rec / auth，15 号 spec）
② 先转换：FrontSpecialDataAssembler.assemble() → 银行协议键 specialData
③ 确认（web-test 弹窗 / 业务系统审核）
④ 后请求：FrontTransApi.transferAuth / resendTransferAuthCode（baseData + specialData）
⑤ LiteFlow 链（校验 → tenantBaseConfigResolve → 路由 → 配置 → dispatch → Handle → 银行 → 归一化）
⑥ 返回 R<FrontTransResult>
```

### 1A.1 接口一：resendTransferAuthCode（授权码申请/重发，bizFunc=26）

**入参 baseData**（`TransferAuthCodeBusinessData extends BaseTransactionBusinessData`，与交易公共结构一致）：

| 字段 | 必填 | 说明 |
|---|---|---|
| tenantId / clientId | 是 | 最小调用方两字段（platformCode/dataSourceId 可回填） |
| storeId | 是 | 发起门店 |
| bizSystemCode / bizTransactionType / bizTransactionId / bizSubTransactionId / bizRequestNo | 是 | 业务关联 |
| bizOrderNo / bizSubOrderNo | 是/否 | 主/子单号（orderNo 用主单号） |
| payStoreNo / payStoreId / recStoreNo / recStoreId | 否 | 门店字段 |
| amount | 是 | 交易金额（分），>0 |
| fee / currency | 否 | 本次实现未上送银行 |

**入参 specialData**（组装器 `transferAuthCodeResend()` 输出；转换输入=标准结构）：

| 协议键 | 转换输入 | 加密 |
|---|---|---|
| payMemberCode | pay.bankEMemberCode | 明文 |
| payAccountNo | pay.bankEAccountId | Handle 内 SM2 |
| recAccountNo | rec.bankEAccountId | Handle 内 SM2（intAcctNo） |

组装输入顶层带 `authType`（`SMS` 本期 / `APP` 预留，AuthType 枚举），适配多授权通道。

**出参（改造后公用 `FrontTransResult`）**：

| 字段 | 来源 |
|---|---|
| frontRespCode / frontRespDesc / specialData | 公共（失败时 desc=银行原文） |
| frontSsn / frontStatus | front 生成 / 受理状态 |
| frontQueryId | 银行 queryId |
| specialData.authType | 授权码类型（SMS/APP），成功时返回 |
| specialData.authOrderNo | 成功时解密后的授权指令号（银行响应 smsIdx 的统一命名，闭环传给接口② auth.authOrderNo） |
| specialData.receiveMobile | 接收手机号（authType=SMS 时返回；APP 时无此键） |
| bankRespCode / bankRespDesc | 银行层码（成功时） |

**约束**：bizOrderNo 长度校验；tranType 固定 2（支付，§3.2 待确认）；每次生成新 transSsn+新 smsIdx（重发即重新申请，不传原指令号）；receiveMobile 解密口径待 §3.1 确认；中信调用返回 F200002。

### 1A.2 接口二：transferAuth（授权转账，bizFunc=45）

**入参 baseData**（`AuthTransferBusinessData extends TransferBusinessData`，**零新增字段，与 transfer 完全公用**）：字段清单同 transfer/consume（上表全部 + fee 空补 0）。

**入参 specialData**（组装器 `transferAuth()` 输出；转换输入=pay/rec 标准结构 + auth 扩展）：

| 协议键 | 转换输入 | 加密 |
|---|---|---|
| payMemberCode / recMemberCode | pay/rec.bankEMemberCode | 明文 |
| payAccountNo / recAccountNo | pay/rec.bankEAccountId | Handle 内 SM2 |
| payName / recName | pay/rec.bankAccountName | Handle 内 SM2 |
| authType | auth.authType（SMS/APP） | 明文 |
| authOrderNo | **auth.authOrderNo（授权指令号=阶段①返回的 authOrderNo，原样回传，命名闭环）** | 明文 |
| authCode | **auth.authCode（用户本次输入验证码）** | Handle 内 SM2 |

> specialData 统一使用 Front 语义键（与接口①返回字段同名闭环）；银行协议键
> `reserve.messageOrderNo/messageCheckCode` 由 Handle 内部映射，调用方不感知。

**出参**：`R<FrontTransResult>` ✅ 已公用（同上表）。

**约束**：specialData 八键必填；functionFlag=9、tranType=01、orderNo=bizOrderNo；渠道表 capability=TRANSFER_AUTH（与普通转账同表按能力区分）；短信指令号必须来自本单阶段①返回的 smsIdx（跨请求由业务系统存储）；中信调用返回 F200002。

### 1A.3 公用化改造点（唯一代码项，本文档不实施）

| # | 现状 | 改造 | 影响 |
|---|---|---|---|

## 3. 差异核对项（需用户/银行文档确认，不推测）

### 3.1 receiveMobile 是否 SM2 密文

- lsym：`res.setReceiveMobile(result.getString("receiveMobile"))` —— **不解密直接使用**
- SaaS：`sm2Crypto.decryptHex(...)` 后放入 specialData
- 风险：若银行实际返回明文手机号，SaaS 解密会失败/产出乱码；若返回密文，lsym 老逻辑拿到的是密文（业务侧一直显示密文）。
- **待确认**：平安 Word（KFEJZB6082 响应 receiveMobile 字段说明）到底是明文还是密文。07 号契约若已有裁决以裁决为准；无裁决时以银行 Word 为准，二选一修正。

### 3.2 验证码申请 tranType 固定为 2（支付）

- lsym：按业务 transType 区分——提现（WD）送 1、支付/转账送 2，即**提现短信验证码也走同一接口**（bizFunc=26 是"申请提现或支付短信动态码"）
- SaaS：当前固定 2。若 SaaS 平安提现（bizFunc=01）不需要短信验证码（当前实现未接入验证码），固定 2 正确；若未来提现也要短信验证码，需扩展。
- **待确认**：SaaS 平安提现是否需要短信验证码场景（当前结论：不需要，tranType=2 保持）。

### 3.3 verifityType 双通道简化

lsym 保留 SMS/CODE 两类验证码字段（verifySmsCode/verifyCode）；SaaS 按 07 号契约统一为单个
`messageCheckCode`（仅短信）。**确认**：07 号契约已裁决仅短信，无需恢复双通道。

## 4. consume 侧对接方案（SaaS catering-consume）

lsym 的授权链业务职责在 consume 侧，SaaS 对应骨架已建（16 号 plan），补实方案：

### 4.1 阶段 1：验证码申请（TransferAuthCodeResendAssembleCheck 补实）

```text
1. buildRequest 数据源（"待账户体系定型后接入"的部分）：
   pay ← compayInfoMaps(付款方)：bankEAccountId/bankEMemberCode
   rec ← compayInfoMaps(收款方)：bankEAccountId
   金额/单号 ← TransSlot.transferTransVo
2. 组装器输入标准结构（15 号 spec）：
   pay（bankEMemberCode + bankEAccountId）+ rec（bankEAccountId）
3. 调 FrontApi.resendTransferAuthCode → R&lt;FrontTransResult&gt;（consume 对接实施时按 07 号契约：
   specialData.authOrderNo/authType/receiveMobile；原 `FrontTransferAuthCodeResult` 已删除）
4. 落地（对应 lsym TransValidLog + transfer_sub 回写）：
   · 业务验证码日志表存：frontSsn、specialData.smsIdx（短信指令号）、receiveMobile
   · 业务子单表回写 transValidSsn/transValidOrderNo，子单状态 → 待验证
```

### 4.2 阶段 2：授权确认（TransferAuthAssembleCheck 补实 + 调用链）

```text
1. 组装器输入：
   pay/rec 标准结构 + auth（messageOrderNo=业务子单表存的 transValidOrderNo、
   messageCheckCode=用户本次输入的验证码）
2. 调 FrontApi.transferAuth
3. 失败/异常补偿（lsym 对等）：子单置失败 + frontRespDesc 回写 + 解冻
4. front 不承担：余额校验、同名校验、冻结/解冻（全部留 consume，与 SaaS
   "Front 不判断业务资格"边界一致）
```

### 4.3 挂链

lsym 编排在 transfer 流程的 verfily/auth 分支节点；SaaS 已预留
`chainConsumeAuth`（TransferAuthAssembleCheck 挂接点）与
`TransferAuthCodeResendAssembleCheck`（服务层直调）。按 16 号 plan 补实后挂链即可，
不需要新建链结构。
