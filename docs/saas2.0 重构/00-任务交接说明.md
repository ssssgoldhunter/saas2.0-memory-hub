## 1. 任务目标

重新设计一套面向内部供应链等业务系统的多银行渠道支付 Front。

新 Front 的目标不是兼容旧系统对象，而是：

1. 向内部业务系统提供统一的交易、账户和查询能力；
2. 交易、查询和后续账户领域各自通过 Registry 按“银行编码 + capability”精确选择能力 Handler；
3. 在银行 Handle 中完成钱包协议组装、签名加密、调用和响应转换；
4. 由 Front 管理租户银行配置和渠道交易流水；
5. 新增银行时不修改公共租户配置对象，不影响既有银行实现；
6. 对外隐藏 `bizFunc`、`channelNo`、银行 URL、密钥和算法等协议细节。

首期银行：

- 中信银行；
- 平安银行。

旧 `fund-catering-front-service` 只作为代码结构和银行接口实现参考，不作为新项目兼容基线。

## 3. 已确认的核心约束

后续设计不得在没有明确讨论的情况下推翻以下约束。

### 3.1 新项目边界

- 这是重新设计的新多银行 Front；
- 老系统只参考 Router、Handle 和银行请求组装方式；
- 不复用老系统的 `operator/orgCode/firstCode` 配置定位方式；
- 不要求兼容旧请求、旧响应和旧数据库结构。

### 3.2 租户和银行

- `platformCode` 表示银行编码；
- 一个租户只能启用一家银行渠道；
- 租户银行配置使用：

```text
tenantId + platformCode
```

- Java 字段使用 `tenantId`；
- JSON、数据库字段可使用 `tenant_id`；
- Front 应校验请求中的 `platformCode` 与租户启用的银行一致。

### 3.3 银行配置

以下配置由 Front 根据 `tenantId + platformCode` 从新配置系统获取：

```text
appId/appKey/url
mchntId/mchntMbrId
银行账户特定静态配置
```

配置系统边界使用 `JSONObject`，经通用组装父类和银行策略转换为：

```text
TenantBankAccountConfig
├─ 跨银行通用强类型字段
└─ accountSpecialData: JSONObject
```

不得创建一个不断增加中信、平安及未来银行专属字段的公共账户配置大对象。
对银行内部通用、但不跨银行的字段，必须保留在对应银行的 `accountSpecialData`。

### 3.4 银行协议参数

以下参数只能由银行 Handle 决定：

```text
bizFunc
channelNo
具体钱包接口路径
签名和加密执行方式
钱包 reserveMap 映射规则
银行响应转换规则
```

业务系统不能通过 `specialData` 指定或覆盖这些参数。

## 4. 已确定的请求结构

### 4.1 对外请求为两部分

```java
public class FrontRequest<T extends FrontBaseRequestData> {
    // 租户、门店、银行及当前业务的银行无关强类型基础数据
    private T baseData;

    // 当前银行、当前接口的特殊数据
    private JSONObject specialData;
}
```

所有强类型基础数据继承公共定位信息：

```java
public class FrontBaseRequestData {
    private String tenantId;
    private String storeId;
    private BankCode platformCode;
}
```

两部分分别是：

1. `baseData`：租户、门店、银行定位信息和交易/交易查询/账户查询的公共强类型字段；
2. `specialData`：`JSONObject` 格式的银行及接口特殊字段。

已确认的公共字段补充约束：

- 交易基础对象包含 `payStoreNo/payStoreId/recStoreNo/recStoreId` 两组收付款门店字段；
- 单笔交易状态查询对象包含 `frontSsn/bizOrderNo/bizSubOrderNo`，其中后两者是业务主流水和业务子流水；
- 交易、交易查询和账户查询请求都通过外层 `FrontRequest.specialData` 提供当前能力的银行特殊字段。

### 4.2 Front 内部上下文

银行路由完成后，`AbstractBankHandle` 根据 `tenantId + bankCode` 加载银行配置并形成：

```java
public record BankRequestContext<T extends FrontBaseRequestData>(
    T baseData,
    JSONObject specialData,
    TenantBankAccountConfig accountConfig) {
}
```

`accountConfig` 不由业务系统传入；外部 `FrontRequest` 仍然只有 `baseData + specialData` 两段。
Application Service 已通过 `FrontFlowContext.from(request, capability)` 把请求转换为统一业务 Slot，
路由后再由 `AbstractBankHandle.prepareContext()` 形成 `BankRequestContext` 并将租户银行配置回填到 Slot。
`capability` 由当前 API 方法固定写入，调用方不得传入；它参与正确领域内
`(BankCode, FrontCapability)` 能力 Handler 精确路由，同时用于日志和渠道流水记录。禁止用它猜测领域、
执行统一能力预校验或在公共 Dispatch 中二次选择方法。
当前已落地 Context、执行阶段、LiteFlow `FlowExecutor`、NodeComponent 和 13 条 EL 规则链；
Application Service 统一通过 `FrontFlowExecutor` 进入规则链，不再直调 Handle。
`TenantBankAccountConfig` 直接承载组装后的银行账户配置：

```text
TenantBankAccountConfig
├─ appId/appKey/url/mchntId/mchntMbrId
└─ accountSpecialData: JSONObject
```

`accountSpecialData` 是租户银行账户的特定静态配置，与当前交易/查询请求的
`specialData` 是两个独立 `JSONObject`，不得合并或相互覆盖。平安账户特定字段为
`txnClientNo/mrchCode/stlAcctNo`，其中 `stlAcctNo` 是资金汇总账号；中信账户特定字段为 `default_role/default_fund_type/self_role/`
`self_fund_type/self_dealType/self_store_no/self_store_id`。中信这 7 个字段对中信各交易能力
是通用账户配置，但不上提到跨银行通用属性。

### 4.3 `specialData` 的边界

`specialData` 使用 `JSONObject`，不使用 `Map<String, String>` 包装多层 JSON 字符串。

可以包含：

- 当前银行和接口特有的可变业务字段；
- 暂未进入公共强类型对象的条件字段；
- 银行特有备注、分润扩展或查询扩展。

不能包含：

- 银行商户和密钥配置；
- 银行账户 `accountSpecialData`；
- `bizFunc`、`channelNo`；
- 银行 URL；
- 签名、加密算法；
- Front 流水生成规则；
- 已经属于公共核心业务语义的金额、订单、账户、查询场景等字段。

每个“银行 + 业务接口 + schemaVersion”必须定义：

- 允许字段白名单；
- 必填和条件必填规则；
- 字段类型、长度、枚举；
- 敏感字段处理方式；
- 到银行 `reserveMap` 的显式映射。

禁止直接把调用方 `specialData` 全量 `putAll` 到银行请求。

## 5. 已确定的路由与 Handle 结构

### 5.1 领域分开，领域内按银行 + capability 精确路由

首期按业务大类建立两个 Registry：

```text
TransactionHandlerRegistry
QueryHandlerRegistry
```

Registry Key：

```text
(BankCode, FrontCapability)
```

其中 `BankCode` 由 `platformCode` 统一解析，capability 由具体 API 方法内部固定。不得把以下内容混入 key：

- `bizFunc`；
- `channelNo`；
- 账户类型；
- 银行交易类型。

API 所属领域已经决定进入 Transaction 或 Query；后续账户维护能力进入独立 Account Registry。禁止统一
Router 再按 capability 名称、前缀或枚举列表猜测领域。

### 5.2 查询使用“银行 + 查询能力”Handler

已确认的查询结构：

```text
QueryHandlerRegistry(bankCode, capability)
  → Citic*QueryCapabilityHandler
  → PingAn*QueryCapabilityHandler
```

每个 Handler 只对应一个查询能力，例如：

```java
queryTransactionStatus(...)
queryPlatformTransactions(...)
querySubAccountTransactions(...)
queryAccountBalance(...)
queryAccountStatus(...)
```

对外 API 已拆成上述具体方法，请求不得额外传 `QueryCapability/FrontCapability`。API 方法在服务内部
固定 capability，Query Registry 按 `(BankCode, FrontCapability)` 直接取得具体 Handler；通用执行节点
调用该 Handler，不再通过公共查询 `switch` 二次分派。

### 5.3 LiteFlow 定位

LiteFlow 用于公共流程编排：

```text
请求校验
→ 当前 API 固定 capability 并进入交易/查询领域链
→ platformCode 解析 BankCode
→ 领域 Registry 按 (BankCode, capability) 选择能力 Handler
→ AbstractBankHandle 装配租户银行配置上下文
→ 重复交易校验
→ 渠道流水预创建
→ Handle 业务方法调用
→ 响应归一化
→ 渠道流水更新
→ 异常处理
```

业务系统可以使用 LiteFlow `SWITCH` 选择对应银行的 `specialData` 组装工具。

Front 内部银行选择仍使用 Router/Handle，不让 LiteFlow 规则直接承载银行协议路由。

### 5.4 新旧 Handle 映射结论

当前 13 个业务 Handle 方法与旧 `fund-catering-front` 的关系已经固定：

- 普通转账、授权转账、消费、退款、提现、平台付款、平台收款均保留旧业务语义；
- 授权码重发对应旧 `sendSmsVerification`；平安没有独立重发协议，当前统一为生成新银行流水后再次
  调用 `bizFunc=26`，不传原短信指令号；
- 账户状态对应旧 `AccountHandle.acctState`，该方法只存在于 lsym 参考版本；
- 账户余额对应旧 `BasTransQueryHandle.queryAccInfo`；
- 新 `queryTransactionStatus` 只映射单笔状态 `queryTransStatus`；中信 `bizFunc=73` 是文件处理状态，
  不得合并进该方法；
- 平台明细固定对应中信 `bizFunc=25/chnlNo=0010`；账户/登记簿明细固定对应中信
  `bizFunc=24/chnlNo=0010`，两者不再按交易类型拆更多 Handle 方法；
- `queryWithDrawFee` 不再保留独立能力，由平台明细/账户交易查询按交易类型覆盖；
- 回执验证码只在平安旧实现中存在，中信对应方法返回 `null`。它实际是“查询明细单验证码”，若后续纳入应按平安特有能力单独设计；
- 转账召回、回执验证码、开户绑卡和文件处理不在首期范围。

完整逐方法映射见 `04-front-service完整重构实施方案.md` 的“11.6 当前 Handle 方法与旧 Front Handle 映射”。

```text
01 转账入金
02 退汇
03 支付渠道入金
04 提现
05 退款（预留）
99 所有
```

单个查询日期和交易类型由业务系统放入请求 `specialData`；Handle 将 `transactionDate` 映射为银行
`TRANS_DATE`，并自行维护银行 `PAGE`。中信 24/25 不支持跨日，`bizFunc/chnlNo/TRANS_DATE/PAGE`
不允许业务系统覆盖。

平安没有完全等价的一个接口：

```text
04 普通转账充值明细
05 会员时间段交易明细
08 清分、提现和部分退款明细
02 提现退票
39 银行费用扣收结果
```

不能假设平安可以用一个 `bizFunc` 返回中信 `25` 的全部分类。

### 7.5 子账户交易明细

中信 `bizFunc=24`：

```text
01 入金分账

03 提现
04 提现手续费
05 提现退汇
06 渠道来账
```

查询日期范围、交易类型和登记簿/账户类型由业务系统放入请求 `specialData`。账户类型当前按中信 v4.7：

```text
01 公共调账登记簿
12 平台自有资金登记簿
13 担保登记簿
17 待结算手续费登记簿
```

平安最接近的是 `bizFunc=05`：

```text
queryFlag=1 全部
queryFlag=2 转出
queryFlag=3 转入
```

平安提现、清分等明细还需要 `bizFunc=08`。

## 8. 渠道交易流水设计约束

Front 渠道流水必须同时按银行和交易业务拆分，不能使用一张统一渠道表：

```text
中信：transfer / consume / refund / withdraw / platform_pay / platform_receive
平安：transfer / consume / refund / withdraw
```

平安 `transferAuth/resendTransferAuthCode` 与普通转账进入平安转账表，由 `capability` 区分；中信不创建
授权空表，平安不创建平台收付款空表。精确表名、字段和索引见 `09-channel-transaction-ddl.md`。

用途：

1. 保存 Front 实际请求银行的数据和最终结果；
2. 关联业务主订单、子订单；
3. 按 `tenantId + bizOrderNo + bizSubOrderNo` 防止重复交易；
4. 退款关联原交易；
5. 状态查询时确定原银行交易类型；
6. 平安退款固定使用 `bizFunc=02`，并按原业务主子流水定位原渠道记录；`bizFunc=06` 本期不启用；
7. 平安状态查询时确定使用 `bizFunc=02/03`；
8. 支持超时、未知状态和后续补偿。

每张表必须保存的字段组：

```text
tenant_id
store_id
capability
front_ssn / front_query_id
biz_system_code / biz_transaction_type
biz_transaction_id / biz_sub_transaction_id
biz_request_no / biz_order_no / biz_sub_order_no
pay_store_no / pay_store_id / rec_store_no / rec_store_id
amount / fee / currency
pay/rec/withdraw/bank_card 相关明确字段
bank_biz_func
bank_channel_no
bank_query_id
bank_user_ssn
wallet_resp_code / wallet_resp_desc
bank_resp_code / bank_resp_desc / bank_status
front_status
reserve1 / reserve2 / reserve3
create_time / update_time / bank_responded_at
```

中信退款表不保存原能力、原渠道记录或原 Front 流水，也不在转账、消费表维护累计退款金额；只保存
本次退款及有效银行报文所需的明确字段。平安退款必须以
`tenantId + originalBizOrderNo + originalBizSubOrderNo` 同时精确查询原平安转账表和消费表；只有唯一命中
才继续，并在退款表保存 `originalCapability/originalChannelTransactionId/originalFrontSsn` 及原收付款字段。
该查询只负责装配银行报文和建立渠道关联，不校验原交易资格或累计退款金额，也不更新原交易表。
业务系统不得传入物理表名或 capability。当前 API 方法固定 capability，领域 Registry 以
`(BankCode, FrontCapability)` 选择具体能力 Handler，Handler 使用固定 Repository；capability 同时写入
渠道流水，但不得在 Handler 定位后再用于动态选表。
渠道表不保存整段请求或响应快照。账户、会员、姓名、卡号等内部业务字段允许按明确列保存原始值，
本期不要求数据库字段加密；日志、异常消息和普通接口响应仍不得输出。

### 8.1 交易状态建议

```text
INIT
SENDING
ACCEPTED
PROCESSING
SUCCESS
FAILED
UNKNOWN
RETURNED
REFUNDED
```

特别注意：

- HTTP 成功不是交易成功；
- 钱包平台受理成功不是银行最终成功；
- 平安提现同步成功只表示受理；
- 超时、无响应不能直接记为失败，应进入 `UNKNOWN` 并主动查询。

## 9. 已确定的统一交易响应

单条接口使用公共 `R` 包装确定类型结果，不再增加 `FrontResponse` 中间层：

```java
R<FrontTransResult>

public class FrontBaseResult {
    private String frontRespCode;
    private String frontRespDesc;
    private JSONObject specialData;
}
```

`R.code/msg` 表示工程统一调用结果；`R.data` 是跨银行公共强类型结果；
`R.data.specialData` 表示银行特殊结果。Front 公共错误码统一放入
`catering-common-core`，功能模块和 API 模块不得重复定义。

分页明细查询分别返回 `TableDataInfo<AccountTransDetailItem>` 和
`TableDataInfo<PlatformTransDetailItem>`，禁止使用 `R` 二次包装。两套行对象各自的 `specialData` 保存
该笔明细对应的银行 `reserveMap` 白名单映射结果。

`specialData` 不得包含密钥等配置数据；日志默认不得打印完整 `specialData`。

交易类统一基础字段：

```text
front_resp_code
front_resp_desc
front_ssn
front_status
front_query_id
front_remark
front_trans_dt
front_trans_tm
```

Java 对象建议使用 camelCase：

```text
frontRespCode
frontRespDesc
frontSsn
frontStatus
frontQueryId
frontRemark
frontTransDate
frontTransTime
```

JSON 是否输出 snake_case 由统一序列化规范决定，不要在不同接口中混用。

查询类后续需要设计各自的：

- 查询基础响应；
- 分页响应；
- 账户余额结果；
- 账户状态结果；
- 交易状态结果；
- 平台交易明细项；
- 子账户交易明细项。

不要让所有查询共用一个包含大量可空字段的大结果对象。

## 16. 2026-08-25 三域注册最终裁决（覆盖前述历史结构）

本节是当前结构交接结论；前文出现的 `FrontFlowContext`、Router、Dispatch、Handle、单一 Registry、
两域注册或多节点链均只用于历史追溯，不得作为下一轮开发模板。

1. 当前执行域固定为 Transaction、Query、Account 三个域。账户状态和账户余额归 Account 域，
   因此当前是三套强类型 Capability 接口、三套 Registry、三个 ExecuteNode 和三个域 Slot。
2. 13 条 LiteFlow chain id 与 API 入口不变：8 条交易链只执行 `frontTransExecute`，3 条交易查询链
   只执行 `frontQueryExecute`，2 条账户链只执行 `frontAccountExecute`。
3. `FrontTransSlot`、`FrontQuerySlot`、`FrontAccountSlot` 均直接继承 `FrontBaseSlot`，继承深度固定两层。
4. 三条执行路径分别为 `域 ApplicationService → 域 ExecuteNode → 域 Registry → 域 Capability`；
   不保留统一 Capability/Registry/ExecuteNode，不新增 Router、Dispatch、Handle 或抽象执行节点。
5. 租户配置链保留清晰格式但彻底压平：`域 ExecuteNode → TenantBankConfigLoader →
   RemoteConfigServiceClient`；删除 `Provider → AssemblerRouter → Assembler` 继承/嵌套链。
6. 银行能力按 `channel/{bank}/{transaction|query|account}` 放置，每个银行每个能力允许少量组装代码重复，
   以单文件可读性和后续快速接入新银行为优先。
7. 钱包发送统一经 `BankWalletGateway.post → BankWalletSender`。Capability 记录业务步骤，Sender 唯一记录
   请求、响应和失败；请求/响应 body 使用完整明文 JSON、不做字段脱敏。
8. `appKey`、私钥、签名材料、签名/认证 Header、`Authorization`、`Cookie` 等非业务报文凭证不属于
   明文 body 要求，仍禁止进入日志。
9. 22 个通用能力归域为 Transaction 12、Query 6、Account 4；中信不明来款继续作为中信专项能力，
   不纳入通用三域框架。
10. 最终设计见 28 号，实施步骤见 29 号；30 号是三域裁决前历史报告，不得用于最终验收。
