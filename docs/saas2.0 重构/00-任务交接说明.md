## 1. 任务目标

重新设计一套面向内部供应链等业务系统的多银行渠道支付 Front。

新 Front 的目标不是兼容旧系统对象，而是：

1. 向内部业务系统提供统一的交易、账户和查询能力；
2. 通过 Router 按银行编码选择银行 Handle；
3. 在银行 Handle 中完成钱包协议组装、签名加密、调用和响应转换；
4. 由 Front 管理租户银行配置和渠道交易流水；
5. 新增银行时不修改公共租户配置对象，不影响既有银行实现；
6. 对外隐藏 `bizFunc`、`channelNo`、银行 URL、密钥和算法等协议细节。

首期银行：

- 中信银行；
- 平安银行。

旧 `fund-catering-front-service` 只作为代码结构和银行接口实现参考，不作为新项目兼容基线。

## 3. 已确认的核心约束

后续设计不得在没有明确讨论的情况下推翻以下约束。

### 3.1 新项目边界

- 这是重新设计的新多银行 Front；
- 老系统只参考 Router、Handle 和银行请求组装方式；
- 不复用老系统的 `operator/orgCode/firstCode` 配置定位方式；
- 不要求兼容旧请求、旧响应和旧数据库结构。

### 3.2 租户和银行

- `platformCode` 表示银行编码；
- 一个租户只能启用一家银行渠道；
- 租户银行配置使用：

```text
tenantId + platformCode
```

- Java 字段使用 `tenantId`；
- JSON、数据库字段可使用 `tenant_id`；
- Front 应校验请求中的 `platformCode` 与租户启用的银行一致。

### 3.3 银行配置

以下配置由 Front 根据 `tenantId + platformCode` 从新配置系统获取：

```text
appId/appKey/url
mchntId/mchntMbrId
银行账户特定静态配置
```

配置系统边界使用 `JSONObject`，经通用组装父类和银行策略转换为：

```text
TenantBankAccountConfig
├─ 跨银行通用强类型字段
└─ accountSpecialData: JSONObject
```

不得创建一个不断增加中信、平安及未来银行专属字段的公共账户配置大对象。
对银行内部通用、但不跨银行的字段，必须保留在对应银行的 `accountSpecialData`。

### 3.4 银行协议参数

以下参数只能由银行 Handle 决定：

```text
bizFunc
channelNo
具体钱包接口路径
签名和加密执行方式
钱包 reserveMap 映射规则
银行响应转换规则
```

业务系统不能通过 `specialData` 指定或覆盖这些参数。

## 4. 已确定的请求结构

### 4.1 对外请求为两部分

```java
public class FrontRequest<T extends FrontBaseRequestData> {
    // 租户、门店、银行及当前业务的银行无关强类型基础数据
    private T baseData;

    // 当前银行、当前接口的特殊数据
    private JSONObject specialData;
}
```

所有强类型基础数据继承公共定位信息：

```java
public class FrontBaseRequestData {
    private String tenantId;
    private String storeId;
    private BankCode platformCode;
}
```

两部分分别是：

1. `baseData`：租户、门店、银行定位信息和交易/交易查询/账户查询的公共强类型字段；
2. `specialData`：`JSONObject` 格式的银行及接口特殊字段。

已确认的公共字段补充约束：

- 交易基础对象包含 `payStoreNo/payStoreId/recStoreNo/recStoreId` 两组收付款门店字段；
- 单笔交易状态查询对象包含 `frontSsn/bizOrderNo/bizSubOrderNo`，其中后两者是业务主流水和业务子流水；
- 交易、交易查询和账户查询请求都通过外层 `FrontRequest.specialData` 提供当前能力的银行特殊字段。

### 4.2 Front 内部上下文

路由和能力校验通过后，`AbstractBankHandle` 根据 `tenantId + bankCode` 加载银行配置并形成：

```java
public record BankRequestContext<T extends FrontBaseRequestData>(
    T baseData,
    JSONObject specialData,
    TenantBankConfigSnapshot tenantBankConfig) {
}
```

`tenantBankConfig` 不由业务系统传入；外部 `FrontRequest` 仍然只有 `baseData + specialData` 两段。
Application Service 已通过 `FrontFlowContext.from(request, capability)` 把请求转换为统一业务 Slot，
路由后再由 `AbstractBankHandle.prepareContext()` 形成 `BankRequestContext` 并将租户银行配置回填到 Slot。
当前已落地 Context 和执行阶段骨架，但仍由 Application Service 直调 Handle；LiteFlow `FlowExecutor`、
NodeComponent 和 EL 规则链尚未接入。
`TenantBankConfigSnapshot.accountConfig` 使用 `TenantBankAccountConfig` 承载银行账户配置：

```text
TenantBankAccountConfig
├─ appId/appKey/url/mchntId/mchntMbrId
└─ accountSpecialData: JSONObject
```

`accountSpecialData` 是租户银行账户的特定静态配置，与当前交易/查询请求的
`specialData` 是两个独立 `JSONObject`，不得合并或相互覆盖。平安账户特定字段为
`txnClientNo/mrchCode/stlAcctNo`，其中 `stlAcctNo` 是资金汇总账号；中信账户特定字段为 `default_role/default_fund_type/self_role/`
`self_fund_type/self_dealType/self_store_no/self_store_id`。中信这 7 个字段对中信各交易能力
是通用账户配置，但不上提到跨银行通用属性。

### 4.3 `specialData` 的边界

`specialData` 使用 `JSONObject`，不使用 `Map<String, String>` 包装多层 JSON 字符串。

可以包含：

- 当前银行和接口特有的可变业务字段；
- 暂未进入公共强类型对象的条件字段；
- 银行特有备注、分润扩展或查询扩展。

不能包含：

- 银行商户和密钥配置；
- 银行账户 `accountSpecialData`；
- `bizFunc`、`channelNo`；
- 银行 URL；
- 签名、加密算法；
- Front 流水生成规则；
- 已经属于公共核心业务语义的金额、订单、账户、查询场景等字段。

每个“银行 + 业务接口 + schemaVersion”必须定义：

- 允许字段白名单；
- 必填和条件必填规则；
- 字段类型、长度、枚举；
- 敏感字段处理方式；
- 到银行 `reserveMap` 的显式映射。

禁止直接把调用方 `specialData` 全量 `putAll` 到银行请求。

## 5. 已确定的路由与 Handle 结构

### 5.1 Router 只负责选银行

首期按业务大类建立两个 Router：

```text
TransactionRouter
QueryRouter
```

Router Key：

```text
platformCode
```

不把以下内容放入 Router Key：

- `QueryCapability`；
- `bizFunc`；
- `channelNo`；
- 账户类型；
- 银行交易类型。

### 5.2 查询使用银行“大 Query Handle”

已确认的查询结构：

```text
QueryRouter(platformCode)
  → CiticQueryHandle
  → PingAnQueryHandle
```

具体查询能力由 Handle 方法确定，例如：

```java
queryTransactionStatus(...)
queryPlatformTransactions(...)
querySubAccountTransactions(...)
queryAccountBalance(...)
queryAccountStatus(...)
```

如果对外 API 拆成上述具体方法，则请求不需要额外传 `QueryCapability`。

如果只暴露一个通用 `/query`，则必须在核心业务数据中传 `QueryCapability`，但它仍然不进入 Route Key。

### 5.3 LiteFlow 定位

LiteFlow 用于公共流程编排：

```text
请求校验
→ Router 与能力校验
→ AbstractBankHandle 装配租户银行配置上下文
→ 幂等校验
→ 渠道流水预创建
→ Handle 业务方法调用
→ 响应归一化
→ 渠道流水更新
→ 异常处理
```

业务系统可以使用 LiteFlow `SWITCH` 选择对应银行的 `specialData` 组装工具。

Front 内部银行选择仍使用 Router/Handle，不让 LiteFlow 规则直接承载银行协议路由。

### 5.4 新旧 Handle 映射结论

当前 13 个业务 Handle 方法与旧 `fund-catering-front` 的关系已经固定：

- 普通转账、授权转账、消费、退款、提现、平台付款、平台收款均保留旧业务语义；
- 授权码重发对应旧 `sendSmsVerification`，但旧接口没有区分首次发送和重发，字段确认时继续核对；
- 账户状态对应旧 `AccountHandle.acctState`，该方法只存在于 lsym 参考版本；
- 账户余额对应旧 `BasTransQueryHandle.queryAccInfo`；
- 新 `queryTransactionStatus` 合并旧 `queryTransStatus/queryTransStatus_73`；
- 平台明细、子账户明细分别对应旧 `queryPlatformTransPages/queryTransPages`；
- `queryWithDrawFee` 不再保留独立能力，由平台明细/账户交易查询按交易类型覆盖；
- 回执验证码只在平安旧实现中存在，中信对应方法返回 `null`。它实际是“查询明细单验证码”，若后续纳入应按平安特有能力单独设计；
- 转账召回、回执验证码、开户绑卡和文件处理不在首期范围。

完整逐方法映射见 `04-front-service完整重构实施方案.md` 的“11.6 当前 Handle 方法与旧 Front Handle 映射”。

## 8. 渠道交易流水设计约束

Front 需要建立独立的渠道交易流水表。

用途：

1. 保存 Front 实际请求银行的数据和最终结果；
2. 关联业务主订单、子订单；
3. 幂等控制；
4. 退款关联原交易；
5. 状态查询时确定原银行交易类型；
6. 平安退款时确定使用 `bizFunc=02/06`；
7. 平安状态查询时确定使用 `bizFunc=02/03`；
8. 支持超时、未知状态和后续补偿。

建议字段：

```text
front_ssn
tenant_id
platform_code
business_type
business_order_no
business_sub_order_no
original_front_ssn
request_id / idempotency_key
bank_biz_func
bank_channel_no
bank_trans_ssn
bank_query_id
bank_user_ssn
bank_trans_dt
bank_trans_tm
request_snapshot
response_snapshot
front_status
created_at
updated_at
```

请求和响应快照必须脱敏或加密存储。

### 8.1 交易状态建议

```text
INIT
SENDING
ACCEPTED
PROCESSING
SUCCESS
FAILED
UNKNOWN
RETURNED
REFUNDED
```

特别注意：

- HTTP 成功不是交易成功；
- 钱包平台受理成功不是银行最终成功；
- 平安提现同步成功只表示受理；
- 超时、无响应不能直接记为失败，应进入 `UNKNOWN` 并主动查询。

## 9. 已确定的统一交易响应

所有接口使用公共 `R` 直接包装确定类型结果，不再增加 `FrontResponse` 中间层：

```java
R<FrontTransactionResult>

public class FrontBaseResult {
    private String frontRespCode;
    private String frontRespDesc;
    private JSONObject specialData;
}
```

`R.code/msg` 表示工程统一调用结果；`R.data` 是跨银行公共强类型结果；
`R.data.specialData` 表示银行特殊结果。Front 公共错误码统一放入
`catering-common-core`，功能模块和 API 模块不得重复定义。

分页查询直接返回 `R<FrontPageResult<TransactionDetailItem>>`。`FrontPageResult` 继承的
`specialData` 保存查询级扩展字段，每条 `TransactionDetailItem.specialData` 保存该笔明细对应的
银行 `reserveMap` 映射结果。

`specialData` 不得包含密钥等配置数据；日志默认不得打印完整 `specialData`。

交易类统一基础字段：

```text
front_resp_code
front_resp_desc
front_ssn
front_status
front_query_id
front_remark
front_trans_dt
front_trans_tm
```

Java 对象建议使用 camelCase：

```text
frontRespCode
frontRespDesc
frontSsn
frontStatus
frontQueryId
frontRemark
frontTransDate
frontTransTime
```

JSON 是否输出 snake_case 由统一序列化规范决定，不要在不同接口中混用。

查询类后续需要设计各自的：

- 查询基础响应；
- 分页响应；
- 账户余额结果；
- 账户状态结果；
- 交易状态结果；
- 平台交易明细项；
- 子账户交易明细项。

不要让所有查询共用一个包含大量可空字段的大结果对象。

### 10.2 中信

1. 中信短信验证码接口只用于用户签约，不是转账鉴权。

3. 交易请求金额通常为分，部分明细响应金额为元。
4. 旧代码的中信验证码实现是模拟成功。
5. 当前退款代码只覆盖了较简单的退款场景。
6. 状态查询存在受理、成功、失败、处理中、退款、退汇等多种状态。

## 14. 当前代码实施状态

当前代码按公共契约与运行时实现分为：

```text
catering-api/catering-api-front
└── API、请求响应模型、常量与枚举

catering-common/catering-common-core
└── 统一返回主体 R、Front 公共错误码与 FrontException

catering-modules/catering-front
└── 功能实现、异常转换与服务配置
```

原 `catering-front-api`、`catering-front-common` 已合并到工程既有的
`catering-api-front`；`catering-front` 本身是 Jar 服务模块并直接依赖该 API 制品及
`catering-common-core`，不再嵌套
`catering-front-service` 子模块。

已实现的骨架：

- 13 个首期 API，统一直接返回 `R<具体结果>`；`FrontBaseResult` 统一提供
  `frontRespCode/frontRespDesc/specialData`；
- `TransactionRouter`、`QueryRouter`；
- 构造器注入 `List<Handle>` 的不可变 Registry；
- 中信、平安 Transaction/Query 四个 Handle Bean；
- `TenantBankConfigProvider`、`TenantBankConfigSnapshot`、`TenantBankAccountConfig` 配置边界；
- 银行账户配置的通用组装父类、平安/中信策略和重复注册校验路由；
- `constant.front` 下集中定义配置查询原始 key 及通用、平安、中信账户配置 `JSONObject` 字段 key；
- `constant.front` 下新增 `FrontBankRequestConstants`、`FrontBankResponseConstants`、`CiticTransferContractKeys`、
  `PingAnTransferContractKeys`，固化 transfer/consume 字段、单位、固定协议值和两家银行不同成功码；
- `CiticTransferContractKeys` 已按 mdl 当前 transfer/consume 实际映射收缩；未使用的
  `USER_SHARE_*`、`REQ_RESERVED` 不作为活动常量，`P_SELF_FLAG/P_SELF_AMT` 当前固定为 `N/0`；
- `BaseTransactionBusinessData` 统一提供单位为分的 `amount/fee`，transfer/consume 对象补齐双方
  账户、会员编号和名称；

  `R.ok(result)` 返回顶层 `R.code=200`，具体银行业务结果只由 data 内统一码和状态表达；
