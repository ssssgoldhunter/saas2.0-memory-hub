## 0. 当前 Front 适配结构

中信通用能力按三个执行域注册，不使用大 Handle：

| 域 | Capability | LiteFlow 入口 |
|---|---|---|
| Transaction | transfer、consume、refund、withdraw、platformPay、platformReceive | `frontTransExecute` |
| Query | transactionStatus、platformTransactionDetails、accountTransactionDetails | `frontQueryExecute` |
| Account | accountStatus、accountBalance、accountOpen、accountBindCard、accountUnbindCard、accountUpdateInfo、accountClose、accountWhiteName、accountWithdraw | `frontAccountExecute` |

每个“中信 × 能力”是所属域强类型 Capability，通过本域 Registry 路由；配置由
`域 ExecuteNode → TenantBankConfigLoader → RemoteConfigServiceClient` 加载，钱包统一经
`BankWalletGateway.post → 中信 BankWalletSender` 发送。

中信不明来款仍是独立专项，不进入上述三域 Registry/LiteFlow；请求和返回均为全字段强类型。

Sender 唯一记录完整明文钱包请求/响应 body，并在通信异常记录结构化失败事件；其他层不得重复。
`appKey`、私钥、签名材料、签名/认证 Header、`Authorization`、`Cookie`、完整银行 URL 等
非业务报文凭证禁止进入日志。

## 2. 接入协议摘要

### 2.1 通讯与报文

- 通讯协议：HTTP/HTTPS RESTful；
- 消息体：JSON，由 `msgHead` 和 `msgBody` 组成；
- 业务路径：`/cwap/account/send/{业务后缀}`；
- 中信钱包渠道号：`0010`；
- 大多数联机交易的 `transSsn` 长度为 40 位；
- `transSsn` 规则：

```text
商户编号 + yyyyMMddHHmmssSSS + 8位序列
```

- 平台商户必须保证流水号不重复；
- 中信在同一交易日内对发起方流水号做重复校验。

### 2.2 请求头与安全

主要请求头：

| 请求头 | 说明 |
|---|---|
| `Content-Type` | `application/json; charset=utf-8` |
| `X-Authorization` | 签名类型和签名值 |
| `X-Version` | 后端版本或灰度控制，可选 |
| `X-Tx-ID` | 全局跟踪 ID |
| `X-Span-ID` | 当前调用节点 ID |
| `X-PSpan-ID` | 父调用节点 ID |

签名和加密要求：

- 普通签名：报文体拼接内部集成平台分配的 Secret 后计算 SM3；
- `SIGN-TYPE` 支持文档约定的 SM3、SM2WithSM3；
- 姓名、卡号、手机号、证件号、短信验证码等敏感信息使用 SM2；
- SM2 曲线：`sm2p256v1`；
- 版本历史已明确移除 `SIGN_INFO`，新 Front 不应继续依赖该字段。

### 2.3 金额与时间

- 交易请求的 `transAmt` 通常以“分”为单位；
- 明细查询部分银行返回金额字段在文档中标注为“元”；
- Front 必须在银行响应转换器中统一金额单位，不能直接透出原始字符串；
- 请求时间一般为 `yyyyMMddHHmmss`；
- 银行交易日期、时间常以 `yyyyMMdd`、`HHmmss` 分开返回。

## 3. 公共请求与响应字段

### 3.1 公共请求字段

| 字段 | 含义 | Front 归属 |
|---|---|---|
| `transSsn` | 发起方交易流水号 | Front 生成 |
| `transTime` | 请求发送时间 | Front 生成 |
| `mchntId` | 接入方编号 | 租户银行配置 |
| `mchntMbrId` | 中信平台商户编号 | 租户银行配置 |
| `bizFunc` | 银行业务用途 | 中信 Capability 确定 |
| `chnlNo` | 银行渠道编号，固定 `0010` | 中信 Capability 确定 |
| `acctNo` | 用户编号、商户编号或登记簿定位值 | 业务核心数据，经加密 |
| `outAcctNo` | 资金转出用户编号 | 业务核心数据，经加密 |
| `inAcctNo` | 资金转入用户编号 | 业务核心数据，经加密 |
| `transAmt` | 交易金额 | 业务核心数据 |
| `remark` | 交易备注 | 业务核心数据 |
| `reserve` | 具体业务的补充域 | Capability 显式映射 |

`bizFunc`、`chnlNo`、商户配置、签名密钥和加密密钥不得由业务系统通过 `specialData` 覆盖。

### 3.2 公共响应字段

| 字段 | 含义 | Front 建议映射 |
|---|---|---|
| `errCode` | 钱包平台返回码 | 只用于平台层成功判定并保存渠道流水，不直接透传 |
| `errInfo` | 钱包平台返回信息 | 只用于平台层成功判定并保存渠道流水，不直接透传 |
| `queryId` | 渠道方查询流水号或发起方流水 | `frontQueryId` |
| `sysRespCode` | 中信渠道返回码 | 银行结果码 |
| `sysRespDesc` | 中信渠道返回说明 | 银行结果说明 |
| `status` | 公共交易状态字段，部分用途忽略 | 不可直接作为最终状态 |
| `reserve` | 银行扩展响应 | 银行响应解析器使用 |

现有接入的中信成功条件是 `errCode=D5000000 && errInfo=success && sysRespCode=00000`。
其中中信 `sysRespCode` 成功码是 **5 个 0**。上述原始值必须转换为 `FrontErrorCode`，真实成功统一返回
`200/成功`，不得把原始银行码写入 `frontRespCode/frontRespDesc`。

Front 统一响应不能只根据 `errCode` 判断业务成功，至少需要同时判断：

1. 钱包平台是否正常受理；
2. `sysRespCode` 是否成功；
3. 当前接口返回的是受理结果还是最终结果；
4. 是否需要通过交易状态查询确认终态。

## 5. 当前交易业务详细摘要

### 5.1 消费与普通转账

银行接口：

```text
POST /cwap/account/send/transfer
bizFunc = 27
chnlNo = 0010
银行产品 = 支付（21000050）
```

公共业务核心数据建议包括：

- 业务主订单号、子订单号；
- 付款用户编号、付款用户名称；
- 收款用户编号、收款用户名称；
- 交易金额；
- 交易日期、交易时间；
- 资金类型；
- 备注；
- 可选分润明细；
- 是否包含平台自有资金及平台出资金额。

中信 `reserve` 主要字段：

| 字段 | 含义 |
|---|---|
| `USER_D_NM` | 付款用户名称 |
| `USER_C_NM` | 收款用户名称 |
| `USER_C_AMT` | 收款用户金额，取 `baseData.amount`，单位为人民币分 |
| `USER_SHARE_ID1..n` | 分润用户编号 |
| `USER_SHARE_NM1..n` | 分润用户名称 |
| `USER_SHARE_AMT1..n` | 分润用户金额 |
| `P_SELF_FLAG` | 是否使用平台自有资金 |
| `P_SELF_AMT` | 平台自有资金金额 |
| `BUSS_ID` | 业务主订单号 |
| `BUSS_SUB_ID` | 业务子订单号 |
| `TRANS_DT` | 业务交易日期 |
| `TRANS_TM` | 业务交易时间 |
| `FUND_TP` | 资金类型 |
| `MEMO` | 业务备注 |
| `laasSsn` | 外联平台流水号 |

钱包基础字段 `transAmt` 同样取 `baseData.amount`，单位为人民币分。中信响应的 `queryId` 映射
`frontQueryId`，`USER_TRANS_DT/USER_TRANS_TM` 映射公共交易日期和时间，银行特有的 `USER_SSN`
放入返回 `specialData`。

> ⚠️ **钱包应答键大小写按接口不统一**（UAT 2026-09-03 实测）：`27 转账`、`23 退款` 与
> `74 交易状态查询` 返回大写 `USER_SSN/USER_TRANS_DT/USER_TRANS_TM`；`2041/2042 平台收付款`
> 返回驼峰 `userSsn/userTransDt/userTransTm`（Front 以 `CiticTransferContractKeys.BANK_WIRE_*`
> 常量解析，仅用于钱包应答，不改变对外 `specialData` 大写契约键）。
> **`26 提现` 应答没有 `USER_SSN` 键**：银行流水（EMSSBPG 形态）在 `queryId` 返回
> （此时 `queryId` 不是 transSsn 回显），另有 `WITH_CHANNEL` 键；
> 凭证下载对该场景已做 74 交易状态查询补号并回填渠道行（见 32/33 号文档）。

上表的 `USER_SHARE_*` 是 Word 文档能力字段，但当前 mdl
`ZxTransTransferHandle/ZxTransConsumeHandle` 没有实际映射，本阶段不进入
`CiticTransferContractKeys` 或请求 `specialData`。当前实际 Capability 使用的
`P_SELF_FLAG/P_SELF_AMT` 固定为 `N/0`。

适配结论：

- 消费和普通转账在中信侧使用同一银行能力；
- Front 仍应通过不同业务接口或 `businessType` 保存不同业务语义；
- `bizFunc=27` 不进入 `specialData`；
- 业务系统只传通用付款方、收款方、金额、订单等数据及少量经约定的扩展字段。

### 5.2 提现

银行接口：

```text
POST /cwap/account/send/withdrawal
bizFunc = 26
chnlNo = 0010
银行产品 = 智能提现（21000014）
```

公共字段：

| 字段 | 说明 |
|---|---|
| `acctNo` | 用户提现传用户编号；平台提现传商户编号 |
| `cardNoEnc` | 提现银行卡号，SM2 加密 |
| `transAmt` | 提现金额，单位分 |
| `remark` | 提现备注 |

中信 `reserve`：

| 字段 | 说明 |
|---|---|
| `WITH_TYPE` | `00` 用户提现；`01` 平台提现 |
| `BUSS_ID` | 提现业务订单号 |
| `TRANS_DT` | 业务交易日期 |
| `TRANS_TM` | 业务交易时间 |
| `FEE_TYPE` | `1` 平台承担；`2` 用户承担 |
| `WITH_ACCNAME` | 提现账户名称 |
| `laasSsn` | 外联平台流水号 |

重要约束：

- 平台提现只能选择平台承担手续费；
- 返回可能包含 `USER_TRANS_DT`、`USER_TRANS_TM`、`PWDID`、`TRANS_ID`、`WITH_CHANNEL`；
- `WITH_CHANNEL` 包含本行卡、银联代付、二代小额、二代大额等通道；
- 新 Front 应把提现类型、手续费承担方式定义成核心业务枚举，而不是银行原始字符串。

### 5.3 退款

> 版本说明：旧 mdl 的 `ZxTransConsumeCancelHandle` 使用 `ZxTransferRequest + zxTransfer +
> bizFunc=27` 做反向转账，不是真退款，禁止迁移。最新 lsym UAT 分支
> `lsym_20260625_limeng_refundTask`（提交 `3dff8255d6`）已经改为
> `ZxRefundRequest + SaasZxInterService.zxRefund + bizFunc=23`，是真退款，可作为本节字段映射的
> 最新代码参考。新 Front 可以参考其“原交易协议字段由上游显式提供”的数据边界，但必须改用本项目
> `baseData + specialData` 契约、银行原始 key 白名单和结构化日志（2026-08-14 起字段值明文，
> 无掩码），不能照搬旧请求对象及日志实现。

银行接口：

```text
POST /cwap/account/send/refund
bizFunc = 23
银行产品 = 退款（21000051）
```

Front 公共业务字段：

- 新退款交易流水号；
- 退款金额，单位分；
- 退款主订单号、退款子订单号；
- 原业务主订单号、原业务子订单号，作为 Front 固定采用的原交易定位方式；
- 退款金额、退款原因及本次退款日期时间。

中信 `reserve` 主要字段及当前 Front 来源：

| 字段 | 银行必填性 | 当前 Front 来源 |
|---|---|---|
| `ORI_USER_D_ID` | 必填 | 请求 `specialData.ORI_USER_D_ID` |
| `ORI_USER_D_NM` | 必填 | 请求 `specialData.ORI_USER_D_NM` |
| `ORI_USER_C_ID` | 必填 | 请求 `specialData.ORI_USER_C_ID` |
| `ORI_USER_C_NM` | 选填 | 请求 `specialData.ORI_USER_C_NM`，有值时上送 |
| `ORI_USER_C_AMT` | 协议选填，当前普通退款固定上送 | 本次 `baseData.amount` |
| `ORI_USER_SHARE_ID1..n` | 条件字段，当前不启用 | 分润退款后续单独设计 |
| `ORI_USER_SHARE_AMT1..n` | 条件字段，当前不启用 | 分润退款后续单独设计 |
| `P_SELF_FLAG` | 必填 | 当前普通退款由 Capability 固定为 `N` |
| `P_DEAL_AMT` | 必填 | 当前普通退款由 Capability 固定为 `0` |
| `REFUND_BUSS_ID` | 必填 | 本次 `baseData.bizOrderNo` |
| `REFUND_BUSS_SUB_ID` | 必填 | 本次 `baseData.bizSubOrderNo` |
| `ORI_BUSS_ID` | 当前 Front 必填 | `baseData.orgBizOrderNo` |
| `ORI_BUSS_SUB_ID` | 当前 Front 必填 | `baseData.orgBizSubOrderNo` |
| `ORI_USER_SSN` | 银行定位替代项，当前 Front 不使用 | 不接收 `orgFrontSsn` 映射，不上送 |
| `ORI_USER_TRANS_DT` | 必填 | 请求 `specialData.ORI_USER_TRANS_DT` |
| `TRANS_DT`、`TRANS_TM` | 必填 | 本次 `baseData.businessDate/businessTime` |
| `FUND_TP` | 必填 | `accountSpecialData.default_fund_type`，不得取 role 字段 |
| `MEMO` | 选填 | `baseData.refundReason` |
| `laasSsn` | 必填 | Capability 生成 |

适配结论：

- 文档支持小于原支付金额的部分退款，当前中信退款允许部分退款；
- 分润退款、平台出资退款需要单独设计强类型对象；
- 银行协议允许 `ORI_BUSS_ID + ORI_BUSS_SUB_ID` 或 `ORI_USER_SSN` 二选一定位，但这是银行协议能力，
  不代表 Front 对外也必须暴露两套定位参数；
- catering-front 固定采用 `orgBizOrderNo + orgBizSubOrderNo`，映射
  `ORI_BUSS_ID + ORI_BUSS_SUB_ID`；`orgFrontSsn/transSsn` 不是中信 `ORI_USER_SSN`，不得直接映射；
- 定位字段之外，`ORI_USER_TRANS_DT`、原付款方和原收款方等字段按各自必填性独立校验。它们由上游
  通过请求 `specialData` 的银行原始 key 提供，Front 不查询本地原渠道表补齐。

### 5.4 平台付款

银行接口：

```text
POST /cwap/account/send/transfer
bizFunc = 2041
银行产品 = 平台付款（21000047）
```

资金方向：

```text
平台自有资金登记簿 → 用户登记簿
```

关键数据：

- 收款用户编号和名称；
- 平台侧由商户自有资金登记簿隐式确定，不上送平台银行账号；
- 交易金额；
- 资金类型、处理类型；
- 业务主订单号、子订单号；
- 业务日期、时间；
- 备注和外联流水。

### 5.5 平台收款

银行接口：

```text
POST /cwap/account/send/transfer
bizFunc = 2042
银行产品 = 平台收款（21000048）
```

资金方向：

```text
用户登记簿 → 平台自有资金登记簿
```

关键数据与平台付款基本对应，但付款用户和收款登记簿方向相反。
平台侧同样由商户自有资金登记簿隐式确定，只上送付款用户编号和名称。

### 5.6 短信验证码

中信存在：

```text
POST /cwap/account/send/gen-auth-code
bizFunc = 27
银行产品 = 短信验证码申请（21000062）
```

但文档明确说明其当前用于用户签约：

- `transType=01`：用户注册；
- `sigctType=01`：签约发送；
- `sigctType=02`：签约验证；
- 发送后返回 `tranId`；
- 验证时上送 `tranId + veriCd`；
- 验证码有效期 120 秒；
- 有频率和失败次数限制。

因此当前结论是：

- 中信不具备已确认的“短信鉴权转账”能力；
- 不应将签约验证码接口包装成转账验证码接口；
- 旧代码中的模拟成功实现不能作为银行能力依据。

## 6. 当前账户查询详细摘要

### 6.1 账户查询接口

统一 API：

```text
POST /cwap/account/send/query-acct-info
chnlNo = 0010
```

| `bizFunc` | 能力 | 主要定位参数 | 主要响应 |
|---:|---|---|---|
| 35 | 交易资金账户余额 | 平台商户信息 | 上日、当前相关余额 |
| 36 | 公共登记簿余额 | 登记簿属性 | 登记簿余额 |
| 46 | 用户余额 | `acctNo=USER_ID`、`registerAttr` | 用户登记簿余额 |

## 7. 当前交易查询详细摘要

### 7.1 交易状态查询

银行接口：

```text
POST /cwap/account/send/query-trans-status
bizFunc = 74
银行产品 = 用户交易状态查询（21000010）
```

银行协议存在多种定位字段，但当前 Front 固定使用调用方明确提供的业务流水，不扫描本地渠道表补查询条件：

- `baseData.originalCapability`：描述被查询的原交易能力，不是当前查询 API capability；
- `baseData.originalTransactionDate → oriTransDate`；
- `baseData.bizOrderNo → reserve.BUSS_ID`；
- `baseData.bizSubOrderNo → reserve.BUSS_SUB_ID`；
- `specialData.acctNo → acctNo`，由 Capability 按协议加密；
- `laasSsn`：Capability 生成的外联平台流水号。

原交易能力与银行字段固定映射：

| 原交易能力 | 银行查询字段 |
|---|---|
| `TRANSFER/CONSUME/REFUND` | `BUSS_ID + BUSS_SUB_ID + TRANS_TYPE=01` |
| `WITHDRAW` | 只上送 `BUSS_ID` |

状态查询不接受 `specialData.transactionType`。`TRANS_TYPE=01` 是具体 Capability 当前固定报文参数：转账、消费
沿用 lsym 生产/uat 实现，退款与中信 Word 协议一致。`frontSsn` 当前只供 Front 返回回显，不映射银行
查询条件。

状态语义：

| 银行状态 | 含义 | Front 建议状态 |
|---|---|---|
| `00` | 已受理 | `ACCEPTED` 或 `PROCESSING` |
| `01` | 成功 | `SUCCESS` |
| `02` | 失败 | `FAILED` |
| `03` | 处理中 | `PROCESSING` |
| `04` | 已退款 | 原交易成功并已退款 |
| `05` | 已退汇 | `RETURNED` |

状态值应按具体银行响应字段再次核对，不得只根据 HTTP 成功或钱包平台成功设置 `frontStatus=SUCCESS`。

### 7.2 子账户/登记簿交易明细

银行接口：

```text
POST /cwap/account/send/query-trans-details
bizFunc = 24
银行产品 = 登记簿交易明细查询（21000029）
```

请求：

- `specialData.acctNo`：用户/子账户业务标识，由 Capability 按中信协议加密映射为顶层 `acctNo`；
- `specialData.transactionDate`：单个查询交易日；银行只支持单日 `TRANS_DATE`，不做跨日展开；
- `specialData.transactionType`：映射 `reserve.TRANS_TYPE`；
- `specialData.accountType`：可选，映射 `reserve.registerAttr`；
- `PAGE`：由 Capability 根据 Front 续查游标生成，银行每页默认 50 条；
- `laasSsn`：Capability 生成的外联流水。

交易类型：

| `TRANS_TYPE` | 含义 |
|---:|---|
| 01 | 入金分账 |
| 02 | 交易划转 |
| 03 | 提现 |
| 04 | 提现手续费 |
| 05 | 提现退汇 |
| 06 | 渠道来账 |
| 98 | 所有，返回明细类型 |
| 99 | 所有，返回汇总类型 |

登记簿/账户类型：

| `accountType` | 含义 |
|---:|---|
| 01 | 公共调账登记簿 |
| 12 | 平台自有资金登记簿 |
| 13 | 担保登记簿 |
| 17 | 待结算手续费登记簿 |

旧 UAT 示例曾传 `registerAttr=00`，但 v4.7 Word 定义为 `01/12/13/17`；当前契约以 Word 为准，
联调确认前不得开放任意账户类型。

关键返回字段：

- 用户编号、用户名称；
- 交易日期、时间；
- 交易类型；
- 中信交易流水号、登记簿流水号；
- 业务主订单号、子订单号；
- 交易金额；
- 资金方向；
- 交易后余额；
- 对手方账号、户名；
- 摘要；
- 总页数。

上述值作为中信查询 `specialData.transactionType` 的独立枚举直接开放，不再定义含义不清的通用“实收”
或“所有”：业务系统必须明确选择 `01/06` 或 `98/99`。

### 7.3 平台交易资金账户明细

银行接口：

```text
POST /cwap/account/send/query-trans-details
bizFunc = 25
银行产品 = 交易资金账户明细查询（21000039）
```

请求：

- `specialData.transactionDate`：单个查询交易日；Capability 映射为 `reserve.TRANS_DATE`；
- `specialData.transactionType`：映射 `reserve.TRANS_TYPE`；
- `PAGE`：由 Capability 根据 Front 续查游标生成，从 1 开始，银行每页默认 20 条；
- `laasSsn`：Capability 生成。

交易类型：

| `specialData.transactionType` | 银行含义 |
|---:|---|
| 01 | 转账入金 |
| 02 | 退汇 |
| 03 | 支付渠道入金 |
| 04 | 提现 |
| 05 | 退款，文档标注预留 |
| 99 | 所有 |

关键返回字段：

- 用户编号、用户名称；
- 交易日期、时间；
- 交易类型；
- 中信交易流水号；
- 交易金额；
- 资金方向；
- 当前余额；
- 银行流水、付款账号、付款名称、付款行；账号和户名默认只保存脱敏快照，不原样返回；
- 业务备注字段。

### 7.4 不明来款专项能力

该能力是中信独有的完整业务闭环，不进入通用 `FrontCapability`、三域 Registry 或 LiteFlow 通用链。
对外固定使用独立强类型 API `CiticUnidentifiedRemittanceApi`，请求和返回均不使用 `specialData`：

| 对外方法 | Front 路径 | 中信接口 | 固定值 | 说明 |
|---|---|---|---|---|
| `queryPages` | `/front/v1/citic/unidentified-remittances/pages` | `/query-trans-details` | `2033/0010` | 从请求页翻至银行最后一页并聚合返回 |
| `process`（退款） | `/front/v1/citic/unidentified-remittances/process` | `/refund` | `2025/0010`，`operateType=0` | 退款补充域按 lsym UAT 方式提升到报文顶层 |
| `process`（重新匹配） | 同上 | `/recharge` | `2023/0010`，`operateType=1` | `transDate/transJrno` 定位，`userId` 可空 |
| `process`（实时清分） | 同上 | `/recharge` | `2023/0010`，`operateType=2` | 额外必填 `registerType/userId` |
| `queryStatus` | `/front/v1/citic/unidentified-remittances/status` | `/query-trans-status` | `2087/0010` | `oriTransStatus`：0 未处理、1 成功、2 处理中 |

租户数据仍复用公共能力：直接请求 DTO 继承 `BaseRequest`，四个公共字段由 Header/Feign 上下文注入，
缺失时 `clientId/platformCode` 使用 `tenant_base_config` 回填，`dataSourceId` 使用分片映射缓存
（`sys_tenant.resourceConfig`，形如 `ds_N`）回填；银行账户配置由 `TenantBankConfigLoader` 加载。
调用方不能传入 `appId/appKey/url/mchntId/mchntMbrId/bizFunc/chnlNo`。

处理和状态查询的定位数据应从 `2033` 列表原行取得。特别是 `2087.oriTransSsn/oriTransDate` 分别取
列表的 `transJrno/transDate`，不得改用处理接口返回的 `frontSsn`。客户账（`accountType=0`）时
`bankNo/acctSeq/acctTransNo/finTransFlag` 均必填；内部账（`1`）不要求这四项。

完整业务接入字段、请求示例和返回处理见
[27-中信不明来款业务接入手册](27-中信不明来款业务接入手册.md)。

## 8. Front 适配结论

### 8.1 中信三域 Capability

```text
citic/transaction：Transfer、Consume、Refund、Withdraw、PlatformPay、PlatformReceive
citic/query：TransStatus、PlatformDetail、TransDetail
citic/account：AccountStatus、AccountBalance、AccountOpen、AccountBindCard、AccountUnbindCard、
               AccountUpdateInfo、AccountClose、AccountWhiteName、AccountWithdraw
citic/unidentified：不明来款独立专项 Channel
```

账户余额内部仍可按已确认的 `AccountScope` 选择中信 35/36/46 报文，但执行域固定为 Account，
不得重新合并到 Query Capability。

### 8.2 `specialData` 边界

本节只适用于通用交易/查询 API。中信不明来款专项 API 按任务裁决使用全字段强类型 DTO，
请求和返回均没有 `specialData`。

可以放入 `specialData`：

- 中信接口特有但未进入通用核心对象的可选字段；
- 明细查询的业务日期范围和当前银行交易类型；
- 登记簿交易明细查询的 `accountType`；
- 分润扩展；
- 特殊登记簿属性；
- 文档明确允许的银行扩展备注。

不能放入 `specialData`：

- `bizFunc`；
- `chnlNo`；
- `mchntId`、`mchntMbrId`；
- 银行地址、密钥、签名和加密算法；
- Front 流水号；
- 银行 `TRANS_DATE/PAGE`；
- 提现类型和手续费承担方式等已经具有跨银行公共语义的字段。

### 8.3 渠道流水要求

交易类至少保存：

- `tenantId`、`platformCode`；
- Front 业务类型；
- `frontSsn`；
- 主订单、子订单；
- 原 `frontSsn`；
- 实际 `bizFunc=27/26/23/2041/2042`；
- 银行流水、查询流水、交易日期时间；
- 明确业务字段和银行定位字段；不保存完整请求/响应报文快照；
- `ACCEPTED/PROCESSING/SUCCESS/FAILED/UNKNOWN/RETURNED` 状态。

## 9. 已发现的风险和待确认项

1. 中信短信验证码接口是用户签约能力，不是已确认的转账鉴权能力。
2. 消费和普通转账都映射 `bizFunc=27`，Front 需要通过自身业务类型和渠道流水区分。
3. 退款是否首期支持部分退款、分润退款、平台出资退款需要产品确认。
4. `24` 查询不定义含义不清的统一“实收”；业务系统通过 specialData 常量明确选择
   `01 入金分账` 或 `06 渠道来账`。
5. `24` 的 `98/99` 分别作为“所有明细/所有汇总”两个独立 specialData 枚举值，不能合并。
6. 明细响应金额存在“元”，交易请求金额使用“分”，必须统一转换。
7. `74` 状态查询的已受理、处理中、成功、退款、退汇必须映射为不同 Front 状态。
8. 版本历史已移除 `SIGN_INFO`，旧实现若仍发送该字段需要重构时删除。
9. 旧代码中的 `null`、模拟成功和硬编码仅能作为结构参考，不能作为银行能力证明。
10. 文件、预清分、实时预付暂不进入首期；中信不明来款已作为专项能力独立实现，不得重新并入通用框架。
