## 2. 接入协议摘要

### 2.1 通讯与报文

- 通讯协议：HTTP/HTTPS RESTful；
- 消息体：JSON，由 `msgHead` 和 `msgBody` 组成；
- 业务路径：`/cwap/account/send/{业务后缀}`；
- 中信钱包渠道号：`0010`；
- 大多数联机交易的 `transSsn` 长度为 40 位；
- `transSsn` 规则：

```text
商户编号 + yyyyMMddHHmmssSSS + 8位序列
```

- 平台商户必须保证流水号不重复；
- 中信在同一交易日内对发起方流水号做重复校验。

### 2.2 请求头与安全

主要请求头：

| 请求头 | 说明 |
|---|---|
| `Content-Type` | `application/json; charset=utf-8` |
| `X-Authorization` | 签名类型和签名值 |
| `X-Version` | 后端版本或灰度控制，可选 |
| `X-Tx-ID` | 全局跟踪 ID |
| `X-Span-ID` | 当前调用节点 ID |
| `X-PSpan-ID` | 父调用节点 ID |

签名和加密要求：

- 普通签名：报文体拼接内部集成平台分配的 Secret 后计算 SM3；
- `SIGN-TYPE` 支持文档约定的 SM3、SM2WithSM3；
- 姓名、卡号、手机号、证件号、短信验证码等敏感信息使用 SM2；
- SM2 曲线：`sm2p256v1`；
- 版本历史已明确移除 `SIGN_INFO`，新 Front 不应继续依赖该字段。

### 2.3 金额与时间

- 交易请求的 `transAmt` 通常以“分”为单位；
- 明细查询部分银行返回金额字段在文档中标注为“元”；
- Front 必须在银行响应转换器中统一金额单位，不能直接透出原始字符串；
- 请求时间一般为 `yyyyMMddHHmmss`；
- 银行交易日期、时间常以 `yyyyMMdd`、`HHmmss` 分开返回。

## 3. 公共请求与响应字段

### 3.1 公共请求字段

| 字段 | 含义 | Front 归属 |
|---|---|---|
| `transSsn` | 发起方交易流水号 | Front 生成 |
| `transTime` | 请求发送时间 | Front 生成 |
| `mchntId` | 接入方编号 | 租户银行配置 |
| `mchntMbrId` | 中信平台商户编号 | 租户银行配置 |
| `bizFunc` | 银行业务用途 | 中信 Handle 确定 |
| `chnlNo` | 银行渠道编号，固定 `0010` | 中信 Handle 确定 |
| `acctNo` | 用户编号、商户编号或登记簿定位值 | 业务核心数据，经加密 |
| `outAcctNo` | 资金转出用户编号 | 业务核心数据，经加密 |
| `inAcctNo` | 资金转入用户编号 | 业务核心数据，经加密 |
| `transAmt` | 交易金额 | 业务核心数据 |
| `remark` | 交易备注 | 业务核心数据 |
| `reserve` | 具体业务的补充域 | Handle 显式映射 |

`bizFunc`、`chnlNo`、商户配置、签名密钥和加密密钥不得由业务系统通过 `specialData` 覆盖。

### 3.2 公共响应字段

| 字段 | 含义 | Front 建议映射 |
|---|---|---|
| `errCode` | 钱包平台返回码 | 只用于平台层成功判定并保存渠道流水，不直接透传 |
| `errInfo` | 钱包平台返回信息 | 只用于平台层成功判定并保存渠道流水，不直接透传 |
| `queryId` | 渠道方查询流水号或发起方流水 | `frontQueryId` |
| `sysRespCode` | 中信渠道返回码 | 银行结果码 |
| `sysRespDesc` | 中信渠道返回说明 | 银行结果说明 |
| `status` | 公共交易状态字段，部分用途忽略 | 不可直接作为最终状态 |
| `reserve` | 银行扩展响应 | 银行响应解析器使用 |

现有接入的中信成功条件是 `errCode=D5000000 && errInfo=success && sysRespCode=00000`。
其中中信 `sysRespCode` 成功码是 **5 个 0**。上述原始值必须转换为 `FrontErrorCode`，真实成功统一返回
`200/成功`，不得把原始银行码写入 `frontRespCode/frontRespDesc`。

Front 统一响应不能只根据 `errCode` 判断业务成功，至少需要同时判断：

1. 钱包平台是否正常受理；
2. `sysRespCode` 是否成功；
3. 当前接口返回的是受理结果还是最终结果；
4. 是否需要通过交易状态查询确认终态。

## 5. 当前交易业务详细摘要

### 5.1 消费与普通转账

银行接口：

```text
POST /cwap/account/send/transfer
bizFunc = 27
chnlNo = 0010
银行产品 = 支付（21000050）
```

公共业务核心数据建议包括：

- 业务主订单号、子订单号；
- 付款用户编号、付款用户名称；
- 收款用户编号、收款用户名称；
- 交易金额；
- 交易日期、交易时间；
- 资金类型；
- 备注；
- 可选分润明细；
- 是否包含平台自有资金及平台出资金额。

中信 `reserve` 主要字段：

| 字段 | 含义 |
|---|---|
| `USER_D_NM` | 付款用户名称 |
| `USER_C_NM` | 收款用户名称 |
| `USER_C_AMT` | 收款用户金额，取 `baseData.amount`，单位为人民币分 |
| `USER_SHARE_ID1..n` | 分润用户编号 |
| `USER_SHARE_NM1..n` | 分润用户名称 |
| `USER_SHARE_AMT1..n` | 分润用户金额 |
| `P_SELF_FLAG` | 是否使用平台自有资金 |
| `P_SELF_AMT` | 平台自有资金金额 |
| `BUSS_ID` | 业务主订单号 |
| `BUSS_SUB_ID` | 业务子订单号 |
| `TRANS_DT` | 业务交易日期 |
| `TRANS_TM` | 业务交易时间 |
| `FUND_TP` | 资金类型 |
| `MEMO` | 业务备注 |
| `laasSsn` | 外联平台流水号 |

钱包基础字段 `transAmt` 同样取 `baseData.amount`，单位为人民币分。中信响应的 `queryId` 映射
`frontQueryId`，`USER_TRANS_DT/USER_TRANS_TM` 映射公共交易日期和时间，银行特有的 `USER_SSN`
放入返回 `specialData`。

上表的 `USER_SHARE_*` 是 Word 文档能力字段，但当前 mdl
`ZxTransTransferHandle/ZxTransConsumeHandle` 没有实际映射，本阶段不进入
`CiticTransferContractKeys` 或请求 `specialData`。当前实际 Handle 使用的
`P_SELF_FLAG/P_SELF_AMT` 固定为 `N/0`。

适配结论：

- 消费和普通转账在中信侧使用同一银行能力；
- Front 仍应通过不同业务接口或 `businessType` 保存不同业务语义；
- `bizFunc=27` 不进入 `specialData`；
- 业务系统只传通用付款方、收款方、金额、订单等数据及少量经约定的扩展字段。

### 5.2 提现

银行接口：

```text
POST /cwap/account/send/withdrawal
bizFunc = 26
chnlNo = 0010
银行产品 = 智能提现（21000014）
```

公共字段：

| 字段 | 说明 |
|---|---|
| `acctNo` | 用户提现传用户编号；平台提现传商户编号 |
| `cardNoEnc` | 提现银行卡号，SM2 加密 |
| `transAmt` | 提现金额，单位分 |
| `remark` | 提现备注 |

中信 `reserve`：

| 字段 | 说明 |
|---|---|
| `WITH_TYPE` | `00` 用户提现；`01` 平台提现 |
| `BUSS_ID` | 提现业务订单号 |
| `TRANS_DT` | 业务交易日期 |
| `TRANS_TM` | 业务交易时间 |
| `FEE_TYPE` | `1` 平台承担；`2` 用户承担 |
| `WITH_ACCNAME` | 提现账户名称 |
| `laasSsn` | 外联平台流水号 |

重要约束：

- 平台提现只能选择平台承担手续费；
- 返回可能包含 `USER_TRANS_DT`、`USER_TRANS_TM`、`PWDID`、`TRANS_ID`、`WITH_CHANNEL`；
- `WITH_CHANNEL` 包含本行卡、银联代付、二代小额、二代大额等通道；
- 新 Front 应把提现类型、手续费承担方式定义成核心业务枚举，而不是银行原始字符串。

### 5.3 退款

> 实现警告：mdl 的 `ZxTransConsumeCancelHandle` 当前使用 `ZxTransferRequest + zxTransfer +
> bizFunc=27` 做反向转账，不是真退款，禁止迁移。mdl 另有尚未接入业务 Handle 的
> `ZxRefundRequest/SaasZxInterService.zxRefund` 客户端入口。新 Front 必须使用下述
> `/refund + bizFunc=23` 真退款协议。

银行接口：

```text
POST /cwap/account/send/refund
bizFunc = 23
银行产品 = 退款（21000051）
```

公共字段：

- 新退款交易流水号；
- 退款金额，单位分；
- 原支付交易关联信息；
- 退款主订单号、退款子订单号；
- 原业务主订单号、原业务子订单号；
- 原支付中信交易流水号和交易日期；
- 原付款方、原收款方及分润方退款金额。

中信 `reserve` 主要字段：

| 字段 | 说明 |
|---|---|
| `ORI_USER_D_ID`、`ORI_USER_D_NM` | 原支付付款方 |
| `ORI_USER_C_ID`、`ORI_USER_C_NM` | 原支付收款方 |
| `ORI_USER_C_AMT` | 原收款方退款金额 |
| `ORI_USER_SHARE_ID1..n` | 原分润用户 |
| `ORI_USER_SHARE_AMT1..n` | 分润退款金额 |
| `P_SELF_FLAG` | 是否涉及平台自有资金 |
| `P_DEAL_AMT` | 平台资金退款金额 |
| `REFUND_BUSS_ID` | 退款业务主订单号 |
| `REFUND_BUSS_SUB_ID` | 退款业务子订单号 |
| `ORI_BUSS_ID` | 原业务主订单号 |
| `ORI_BUSS_SUB_ID` | 原业务子订单号 |
| `ORI_USER_SSN` | 原中信侧交易流水号 |
| `ORI_USER_TRANS_DT` | 原交易日期 |
| `TRANS_DT`、`TRANS_TM` | 本次退款日期、时间 |
| `FUND_TP` | 资金类型 |
| `MEMO` | 备注 |
| `laasSsn` | 外联平台流水号 |

适配结论：

- 文档支持小于原支付金额的退款，需明确首期是否开放部分退款；
- 分润退款、平台出资退款需要单独设计强类型对象；
- Front 应优先通过 `originalFrontSsn` 查询原渠道流水，补全原银行流水和原交易信息。

### 5.4 平台付款

银行接口：

```text
POST /cwap/account/send/transfer
bizFunc = 2041
银行产品 = 平台付款（21000047）
```

资金方向：

```text
平台自有资金登记簿 → 用户登记簿
```

关键数据：

- 收款用户编号和名称；
- 交易金额；
- 资金类型、处理类型；
- 业务主订单号、子订单号；
- 业务日期、时间；
- 备注和外联流水。

### 5.5 平台收款

银行接口：

```text
POST /cwap/account/send/transfer
bizFunc = 2042
银行产品 = 平台收款（21000048）
```

资金方向：

```text
用户登记簿 → 平台自有资金登记簿
```

关键数据与平台付款基本对应，但付款用户和收款登记簿方向相反。

### 5.6 短信验证码

中信存在：

```text
POST /cwap/account/send/gen-auth-code
bizFunc = 27
银行产品 = 短信验证码申请（21000062）
```

但文档明确说明其当前用于用户签约：

- `transType=01`：用户注册；
- `sigctType=01`：签约发送；
- `sigctType=02`：签约验证；
- 发送后返回 `tranId`；
- 验证时上送 `tranId + veriCd`；
- 验证码有效期 120 秒；
- 有频率和失败次数限制。

因此当前结论是：

- 中信不具备已确认的“短信鉴权转账”能力；
- 不应将签约验证码接口包装成转账验证码接口；
- 旧代码中的模拟成功实现不能作为银行能力依据。

## 6. 当前账户查询详细摘要

### 6.1 账户查询接口

统一 API：

```text
POST /cwap/account/send/query-acct-info
chnlNo = 0010
```

| `bizFunc` | 能力 | 主要定位参数 | 主要响应 |
|---:|---|---|---|
| 35 | 交易资金账户余额 | 平台商户信息 | 上日、当前相关余额 |

| 2058 | 用户状态 | `acctNo=USER_ID` | 用户状态、审核状态等 |

中信登记簿属性可能包括：

- 用户普通登记簿；
- 公共调账登记簿；
- 自有资金登记簿；
- 担保登记簿；
- 待结算手续费登记簿；
- 交易资金账户；
- 剩余可透支额度等。

Front 不应以一个含大量可空字段的结果对象覆盖全部语义。建议至少拆为：

- `PlatformAccountBalanceResult`；
- `SubAccountBalanceResult`；
- `AccountStatusResult`。

### 7.1 交易状态查询

```text
POST /cwap/account/send/query-trans-status
bizFunc = 74
银行产品 = 用户交易状态查询（21000010）
```

主要查询条件：

- `USER_ID`：一般为付款用户编号；
- `USER_SSN`：中信侧交易流水号；
- `ORI_REQ_SSN`：原发起方流水号；
- `BUSS_ID + BUSS_SUB_ID`：业务主、子订单号；
- `ORI_TRANS_DT`：跨日或指定场景的原交易日期；
- `TRANS_TYPE`：支付、退款、平台补贴、平台扣罚等场景条件字段；
- `laasSsn`：外联平台流水号。

应优先使用 Front 渠道流水保存的：

```text
frontSsn
bankUserSsn
bankQueryId
businessOrderNo
businessSubOrderNo
bankTransDate
```

状态语义：

| 银行状态 | 含义 | Front 建议状态 |
|---|---|---|
| `00` | 已受理 | `ACCEPTED` 或 `PROCESSING` |
| `01` | 成功 | `SUCCESS` |
| `02` | 失败 | `FAILED` |
| `03` | 处理中 | `PROCESSING` |
| `04` | 已退款 | 原交易成功并已退款 |
| `05` | 已退汇 | `RETURNED` |

状态值应按具体银行响应字段再次核对，不得只根据 HTTP 成功或钱包平台成功设置 `frontStatus=SUCCESS`。

### 7.2 子账户/登记簿交易明细

银行接口：

```text
POST /cwap/account/send/query-trans-details
bizFunc = 24
银行产品 = 登记簿交易明细查询（21000029）
```

请求：

- `TRANS_DATE`：查询日期；
- `PAGE`：页码，默认每页 50 条；
- `TRANS_TYPE`：交易类型；
- `registerAttr`：可选登记簿类型；
- `acctNo`：用户编号；
- `laasSsn`：外联流水。

交易类型：

| `TRANS_TYPE` | 含义 |
|---:|---|
| 01 | 入金分账 |
| 02 | 交易划转 |
| 03 | 提现 |
| 04 | 提现手续费 |
| 05 | 提现退汇 |
| 06 | 渠道来账 |
| 98 | 所有，返回明细类型 |
| 99 | 所有，返回汇总类型 |

关键返回字段：

- 用户编号、用户名称；
- 交易日期、时间；
- 交易类型；
- 中信交易流水号、登记簿流水号；
- 业务主订单号、子订单号；
- 交易金额；
- 资金方向；
- 交易后余额；

- Front 通用“实收”对应 `01 入金分账` 还是 `06 渠道来账`；
- “所有”是否明确拆成“所有明细”和“所有汇总”。

## 8. Front 适配结论

### 8.1 建议的中信 Handle 能力

```text
CiticTransactionHandle
  - consume
  - transfer
  - withdraw
  - refund
  - platformPay
  - platformReceive

CiticAccountHandle
  - queryPlatformBalance
  - querySubAccountBalance
  - queryAccountStatus

CiticQueryHandle
  - queryTransactionStatus
  - queryPlatformTransactions
  - querySubAccountTransactions
```

### 8.2 `specialData` 边界

可以放入 `specialData`：

- 中信接口特有但未进入通用核心对象的可选字段；
- 分润扩展；
- 特殊登记簿属性；
- 文档明确允许的银行扩展备注。

不能放入 `specialData`：

- `bizFunc`；
- `chnlNo`；
- `mchntId`、`mchntMbrId`；
- 银行地址、密钥、签名和加密算法；
- Front 流水号；
- 会改变公共业务语义但应强类型表达的查询类型、提现类型和手续费承担方式。

### 8.3 渠道流水要求

交易类至少保存：

- `tenantId`、`platformCode`；
- Front 业务类型；
- `frontSsn`；
- 主订单、子订单；
- 原 `frontSsn`；
- 实际 `bizFunc=27/26/23/2041/2042`；
- 银行流水、查询流水、交易日期时间；
- 脱敏后的请求、响应；
- `ACCEPTED/PROCESSING/SUCCESS/FAILED/UNKNOWN/RETURNED` 状态。

## 9. 已发现的风险和待确认项

1. 中信短信验证码接口是用户签约能力，不是已确认的转账鉴权能力。
2. 消费和普通转账都映射 `bizFunc=27`，Front 需要通过自身业务类型和渠道流水区分。
3. 退款是否首期支持部分退款、分润退款、平台出资退款需要产品确认。
4. `24` 查询的“入金分账”和“渠道来账”都可能被业务称为“实收”，需要统一定义。
5. `24` 的 `98/99` 分别是所有明细、所有汇总，不能合并成一个含义不清的“所有”。
6. 明细响应金额存在“元”，交易请求金额使用“分”，必须统一转换。
7. `74` 状态查询的已受理、处理中、成功、退款、退汇必须映射为不同 Front 状态。
8. 版本历史已移除 `SIGN_INFO`，旧实现若仍发送该字段需要重构时删除。
9. 旧代码中的 `null`、模拟成功和硬编码仅能作为结构参考，不能作为银行能力证明。
10. 文件、预清分、不明来账、实时预付暂不进入首期，但需要在能力矩阵中保留为后续扩展项。
